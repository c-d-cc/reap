# agent 층 — context와 skill

## context와 skill


### 역할 분담

**판단은 skill이, 확정은 도구가 한다.**

도구가 소유하는 것은 확률에 맡길 수 없는 일뿐이다: 이미 쓰여진 것을 조립해 세션에 넣는 일, append-only 로그에 출처를 부착하는 일, id와 frontmatter를 확정하는 일.

### ctx가 조립하는 것

```bash
reap ctx [--milestone <ms-id>] [--hook]
```

`genome/` 전체, `environment/summary.md`, 그리고 **상태 줄**. 그것이 전부다.

**milestone의 본문도 `memory/`도 `idea/`도 조립하지 않는다.** `milestone.md`도 `handoff.md`도 `tasks/`도 마찬가지다. 상태 줄이 그것들이 어디 있는지 말하고, **무엇을 읽을지는 agent가 정한다.**

`--hook`은 같은 본문을 `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext": "..."}}`에 담아 낸다. 이스케이프는 문자열을 만든 쪽이 한다. 실을 것이 없거나 REAP 프로젝트가 아니면 아무것도 내지 않고 성공으로 끝난다.

**싣지 않는다** — `environment/resources/`, 세대 기록의 본문, 아카이브된 milestone.

미읽은 메시지 개수는 싣지 않는다. 메시지함은 Claude Code가 소유하므로 REAP가 볼 수 없고, 볼 수 없는 것을 세는 척하면 0이 "없음"인지 "모름"인지 구별되지 않는다.

### 왜 milestone 본문은 조립하지 않는가

**맥락 구성은 판단이기 때문이다.**

이 세대에 `milestone.md` 전체가 필요한지 종료 조건만 보면 되는지, 어느 task 파일을 열어야 하는지, `handoff.md`까지 봐야 하는지는 매번 다르다. 고정 목록으로 못 박으면 어떤 세대에는 과하고 어떤 세대에는 모자라며, **과한 쪽은 조용하다** — 확정된 지식의 자리를 밀어낸 것을 아무도 세지 않는다.

원칙 2가 도구에 주는 것은 "확률에 의존하면 **안 되는** 것"이다. 훅 주입이 거기 해당하는 이유는 그것이 **agent가 개입할 수 없는 시점**이기 때문이다 — 첫 토큰 이전이므로 판단할 주체가 아직 없다. 작업 중의 읽기는 그렇지 않다. agent가 있고, 파일을 읽는 도구가 있고, 무엇이 필요한지 아는 상황이 있다.

**그러므로 맥락을 조립하는 별도의 skill도 두지 않는다.** `evolve`가 이미 "무엇을 할 것인가"를 정하며 필요한 것을 읽고, `complete`가 닫으며 `handoff.md`를 다룬다. skill을 하나 더 만들면 "언제 그것을 부르는가"가 하나 더 생기고, skill이 늘수록 각각이 안 불릴 확률이 는다.

### 상태 줄 — 자율에 필요한 지도

agent가 `handoff.md`를 읽으려면 그것이 존재한다는 것과 어디 있는지를 알아야 한다. **그것은 판단이 아니라 사실이므로 도구가 준다.**

```
응답 언어: ko
현재 milestone: ms-004 인증 세션 관리 개편 (focus, open)
  .reap/vision/milestones/ms-004-auth-session/
    milestone.md · handoff.md
    tasks/1-1-storage.md · tasks/1-2-id-and-documents.md · tasks/1-3-ctx.md
열린 세대: gen-0042-exec 세션 토큰 회전 — .reap/life/generations/gen-0042-exec-token-rotation.md
  2026-08-22T10:00:00Z 시작, 시작 커밋 1a2b3c4
기억: .reap/vision/memory/lessons.md
덜 단단한 것: .reap/idea/ (research 3 · freememo 1)
구조: .reap/map.md
작업을 시작하면 /reap:evolve, 마무리하면 /reap:complete
```

`config.language`가 있으면 응답 언어 줄을 낸다. 없으면 안 낸다.

**이번 세대가 열 만한 것은 이름을, 있다는 사실만 알면 되는 것은 개수를 낸다.**

milestone의 문서와 `tasks/`는 이름이다 — 지금 여는 세대가 그중 하나를 실제로 연다. "tasks/ (5개)"라고 쓰면 agent가 디렉토리를 다시 읽어야 하고, 그러면 지도의 값이 절반으로 준다.

`idea/`는 개수다. 수십 개가 될 수 있고 대부분은 지금 하는 일과 무관하다. 이름을 다 늘어놓으면 지도가 아니라 목록이 되고, **목록이 길어지면 지도의 나머지가 안 읽힌다.** 무엇이 있는지 봐야 할 때 agent가 디렉토리를 읽는다.

빈 파일은 이름을 내지 않는다 — 열어봐야 아무것도 없는 곳으로 보내지 않는다. 빈 디렉토리도 줄 자체를 내지 않는다.

**열린 세대를 알리는 것이 이 줄의 핵심이다.** 세션이 중간에 죽고 다음 세션이 그 사실을 모르면 `evolve`가 새 세대를 열어버리고, 그 잘못은 아무 데서도 드러나지 않는다 — `doctor`가 나중에 방치된 generation으로 보고할 뿐이다.

milestone이 없으면 그 묶음을 내지 않고, 열린 세대가 없으면 그 줄을 내지 않는다. **마지막 안내 줄은 항상 낸다.**

### memory도 주입하지 않는다

`memory/`는 **누적되는 문서**다. `lessons.md`는 프로젝트가 사는 동안 계속 자라고, 자라는 문서를 매 세션 싣는 것은 그 자체로 잘못된 거래다 — 오늘 필요 없는 교훈 서른 개가 오늘 필요한 지식의 자리를 밀어낸다.

`genome/`은 다르다. 처방이고 규칙이며 사람이 관리하므로 유계다. 자라면 그것이 곧 신호다.

**대신 memory에는 나가는 문을 둔다.** 그것이 없으면 지도에만 두는 것으로도 문제가 해결되지 않는다 — 파일이 계속 자라 결국 아무도 안 읽는다.

상태를 skill에 맡기지 않는 이유는 바인딩을 도구에 둔 이유와 같다. agent가 매번 `.session`을 정확히 읽고 정확히 해석할 것을 기대하는 것이 곧 확률에 거는 것이다.

### 이 설계가 무는 대가

**milestone 맥락이 세션에 자동으로 들어오지 않는다.** 사용자가 "이 버그 고쳐줘"라고 하고 agent가 아무것도 열어보지 않으면, spec이 이미 정해둔 접근을 모른 채 다른 길로 간다.

받는 이유는 두 실패의 성질이 다르기 때문이다. 전부 주입하는 낭비는 **매번 확실히** 발생하고 사람이 그것을 느낀다. 맥락 없이 일하는 실패는 **가끔** 발생하고 조용하다 — 그러나 상태 줄이 매 세션 지도와 입구를 보여주고, `genome/evolution.md`가 그것을 규칙으로 못박을 수 있다.

**이 거래가 틀렸다고 판정되면 뒤집을 것은 조립 목록이 아니라 상태 줄이다.** 무엇을 더 주입할지가 아니라, 지도가 충분히 읽히는지를 먼저 본다.

### 무엇을 어느 파일에 쓰는가

`ctx`가 milestone 본문을 조립하지 않으므로 남는 질문은 하나다 — **agent가 무엇을 열게 될 것인가.**

가르는 질문은 같다. **안 읽고 일을 시작하면 무엇이 조용히 잘못되는가.** 종료 조건을 모르면 경계 없이 일하고 그것은 milestone이 끝난 뒤에야 드러난다. 어느 task의 함정을 모르는 것은 그 task를 시작할 때 읽으면 되고, 안 읽었다는 사실도 그때 드러난다.

앞의 것은 `milestone.md`에, 뒤의 것은 `tasks/`에 쓴다. **파일을 나누는 이유는 주입량이 아니라, 필요한 것만 열 수 있게 하기 위해서다.** 한 파일에 다 있으면 경계를 확인하려는 agent가 끝난 task의 상세까지 함께 읽는다 — 그리고 그 낭비는 조용하다.

`environment/`가 이미 같은 모양이다. `summary.md`는 매 세션 주입되고 `resources/`는 필요할 때 읽힌다. 다른 점은 milestone 쪽은 주입되는 것이 하나도 없다는 것뿐이다.

### 절 단위로 자르지 않는다

"`milestone.md`에서 종료 조건 절만 읽는다"는 도구가 할 수 없다. REAP는 본문에 고정 제목을 두지 않으므로 절을 식별할 수단이 없고, 하려면 제목을 다시 고정해야 한다 — REAP의 5단계가 굳은 경로 그대로다.

크기로 자르는 것도 답이 아니다. 어느 문서든 중요한 대목이 앞에 온다는 보장이 없고, 잘린 자리가 문서마다 달라 읽는 쪽이 무엇을 못 봤는지 모른다.

**그래서 경계는 파일이고, 그것을 정하는 것은 쓰는 쪽이다.** agent는 절을 골라 읽을 수 없지만 파일은 골라 열 수 있다.

### 배포하는 skill 9종

플러그인의 `skills/<name>/SKILL.md`에 담기고 `/reap:<name>`으로 불린다. **agent가 REAP를 다루는 통로는 skill이며, skill이 확정적인 부분에서만 CLI를 호출한다.** 그 반대가 아니다.

| skill | 언제 | 무엇을 |
|---|---|---|
| `evolve` | 세대를 열 때 | **plan·exec·fix 중 무엇인지 먼저 판단하고**, 지금 열어도 되는지, exec이면 **어느 근거(milestone 또는 backlog 항목)로** 무엇을 제목으로 여는지 정한다. `reap make generation`을 호출하고, 기록 어휘를 참고해 의도를 적는다. **그다음은 자율 구간이다** — 맥락을 조립하는 skill로 넘기지 않는다(위의 `왜 milestone 본문은 조립하지 않는가`) |
| `complete` | 세대를 닫을 때 | **커밋 규칙 확인**(`git status --porcelain`, 시작 커밋 이후 커밋 유무), 커밋을 어떻게 나누는지, 기록 마무리, `handoff.md` 갱신, backlog 이월 판단, abort 여부. 확인이 끝나면 `reap mark generation --closed` |
| `loop` | 새 의도를 만들 때 — 기획·설계·화면·아직 자리 없는 것 | **loop를 열고 닫는다**(`make loop` · `mark loop --closed`). 유형을 정하고, 열린 loop 중 이어갈 것이 있는지 보고, plan source에 **쓴다** — 아래 **loop** 절의 여섯 판단. 산출물이 자리를 찾았는지 판단해 `carve-milestone`을 부르고 닫는다. `Dialogue`를 기록에 남긴다 |
| `carve-milestone` | loop 안에서, 그리고 milestone을 닫을 때 | plan source를 읽고 실행 가능한 milestone으로 자른다. **자르기 전에 그 계획의 전제를 실제 흔적에 대보는 것**이 첫 동작이다. 크기 기준, 경계·종료조건·범위밖을 정하는 법, plan 인용법, fitness 질문을 자를 때 미리 쓰는 것. 그리고 **종료 절차 전체** — fitness → `cleanup` → `mark milestone --closed`. `complete`는 이 절차를 옮겨 적지 않고 가리키기만 한다 |
| `orchestrate` | 병렬 작업 시 | 역할 명명, 메시지 kind 관례, 언제 claim을 잡는지, barrier 배치, 조율자 패턴 |
| `cleanup` | 사람의 fitness로 milestone을 닫기로 한 뒤, `mark milestone --closed`를 부르기 전 | `life/generations/`를 훑어 **참고 가치가 다한 세대**를 `archive/generations/`로 내린다. 기준은 milestone 소속이 아니라 "앞으로 이것을 볼 일이 있는가"이며, 그 답은 frontmatter에 없으므로 판단이다. CLI(`mark generation --archived`)는 이동만 한다. `mark milestone --closed`보다 먼저 도는 이유는 그것이 milestone 디렉토리(와 `handoff.md`)를 archive로 옮기기 때문이다 |
| `interview` | 의도가 모호할 때, 언제든 | 모호한 요구를 질문으로 구체화한다. 아래 **interview** 절 |
| `init` | **프로젝트당 한 번, 맨 처음** — 새 폴더든 기존 코드베이스든 `.reap/`가 씨앗인 채 남았든 | `reap init`을 부르고 **정본 지식을 세운다** — plan source 등록, `environment/summary.md`, `genome/application.md`·`evolution.md`. 질문지를 갖되 묻는 법은 `interview`를 가리킨다. 아래 **init** 절 |
| `report-issue` | REAP 자체의 결함이나 빠진 기능을 만났을 때 | 누구의 문제인지 가르고(REAP의 것만), 재현을 확정하고, REAP가 소유하는 사실만 실어(`--version`·플러그인 버전·레이아웃 이름) `c-d-cc/reap`에 issue를 올린다. `gh`가 없으면 본문을 사람에게 낸다. 이 프로젝트의 코드·경로·기록 본문은 싣지 않는다 — 공개 리포다. URL은 이 프로젝트의 backlog에 남긴다 |

### init — 정본 지식을 세운다

`reap init`(CLI)은 디렉토리와 씨앗을 놓을 뿐이다. 씨앗은 내용이 아니라 **질문 문장**이고, `ctx`는 `genome/` 전체를 매 세션 주입하므로 **씨앗이 안 채워지면 모든 세션이 빈 프롬프트를 맥락으로 받는다.** 그리고 자리를 만들어두면 나중에 채워진다는 가정은 이 리포에서 세 번 틀렸다 — `context.md`가 21세대 동안 0바이트였고, `conventions/`의 되먹임이 0회였고, genome은 부트스트랩 이후 45세대 동안 거의 안 자랐다(`application.md` 22줄 그대로). **그래서 첫날 제대로 채우는 절차가 필요하고, 그것이 `init` skill이다.**

**"맥락을 조립하는 별도의 skill을 두지 않는다"에 걸리지 않는 이유** — 그 원칙이 막는 것은 `evolve`·`complete`와 경합해 "언제 부르는가"를 하나 더 만드는 skill이다. `init`의 트리거는 **프로젝트당 한 번, 맨 처음**이라 어느 skill과도 경합하지 않는다. 대신 상태 줄이 안내할 수 없는 유일한 skill이다 — `.reap/`가 없으면 훅이 아무것도 주입하지 않으므로 **사람이 명시적으로 부른다.**

**진입 조건이 셋이다.**

| 상태 | `init`이 하는 일 |
|---|---|
| 새 폴더 — 코드 없음 | 사람에게 묻는 것이 거의 전부 |
| 기존 코드베이스 — 코드 있음, `.reap/` 없음 | 읽어서 초안을 쓰고 **확인형**으로 받는다 |
| `.reap/`가 씨앗인 채 남음 | 씨앗으로 남은 자리만 채운다. **씨앗인지는 번들 템플릿과 내용이 같은지로 판정한다** — `reap init --check`가 보고한다(쓰지 않는다). 사람이 한 글자라도 쓴 파일은 건드리지 않는다 |

**순서 — 정본이 어디 있는지부터 정한다.**

1. `reap init` — 디렉토리와 씨앗
2. 탐색 (기존 코드베이스일 때)
3. **plan source 등록** — 기획 문서가 있으면 `make plan-source`
4. `environment/summary.md`
5. `genome/application.md`
6. `genome/evolution.md`
7. 첫 milestone 판단 → `carve-milestone`에 넘긴다

**3이 4·5보다 먼저인 것이 이 순서의 핵심이다.** `application.md`는 plan source에 있는 규범을 옮겨 적지 않으므로, **plan source가 있는지 모르면 `application.md`에 무엇을 쓸지가 안 정해진다.** 뒤집으면 옮겨 적고 나서 중복을 발견한다. `evolution.md`가 마지막인 이유는 앞의 넷을 채우는 동안 그 프로젝트를 이미 겪은 뒤에 쓰는 것이 낫기 때문이다.

**plan source가 없으면 `application.md`가 유일한 자리지만 커지지 않는다.** 기획과 겹치는 부분이 애초에 작다(이 리포의 `application.md`가 그 실물이다). 그래서 **`application.md`가 기획을 담기 시작하면 그것은 plan source가 필요하다는 신호다** — `init` 뒤에도 계속 쓰이는 판정이다.

**안 건드리는 것 둘. 이유가 다르다.** `genome/invariants.md`는 **사람만 수정하기 때문**이고(영구 규칙), `vision/memory/lessons.md`는 **겪은 것이 없기 때문**이다(이 시점의 사실). 같은 문장으로 묶으면 나중에 `lessons.md`를 못 채우게 된다.

**탐색은 소스 파일을 읽지 않는다.** 읽는 것은 매니페스트·락파일, 빌드/테스트 진입점, `README`, 디렉토리 트리 1~2단계, 최근 git log, 그리고 **기존 AI 지침 파일**(`CLAUDE.md`·`AGENTS.md` 등)이다. `summary.md`가 담는 것은 *"다음 세션이 어디서부터 손대야 하는지"*이지 코드의 내용이 아니고, 코드를 읽어 아는 일은 코드 인덱스의 것이다.

**기존 AI 지침 파일이 `evolution.md`의 유일한 직접 재료다.** 코드에서 유추할 수 없는 유일한 항목이라 이 파일이 있고 없고가 온보딩의 질을 가른다. 그런데 `genome/`은 REAP 훅이, `CLAUDE.md`는 클라이언트가 각각 주입하므로 겹치면 같은 것이 두 번 실린다. `init`은 **읽되 고치지 않고, 겹친다는 사실을 사람에게 보고한다.** 남의 파일을 조용히 정리하면 어느 것이 정본인지가 사라진다 — `doctor`가 보고만 하는 것과 같은 결이다.

**확인할 수 없는 것은 쓰지 않는다.** *"이 프로젝트는 TDD를 한다"*고 쓰려면 테스트가 실재하고 돌아간다는 근거가 있어야 한다. 근거가 없으면 쓰지 않고 묻는다.

**탐색의 산출물이 `interview`와의 계약이다.** 탐색이 끝나면 **초안**(근거가 있어 확정한 것)과 **확정된 질문 목록**(사람에게 가야 하는 것)이 나온다. `interview`가 *"남은 모호성 개수를 보여준다"*를 지키려면 질문 수가 묻기 전에 확정돼 있어야 하므로, 절차는 **탐색 → 질문지 확정 → `interview` 호출**이지 채우면서 묻는 것이 아니다. 새 폴더에서는 초안이 거의 비고 질문지가 거의 전부다 — 같은 절차의 양 끝이지 다른 흐름이 아니다.

**`init`은 질문지를 갖고 묻는 법은 갖지 않는다.** *"한 번에 하나"* 같은 문장이 `init`에 한 줄이라도 들어가면 규율의 소유자가 둘이 된 것이다. `init`은 무엇을 어느 순서로 묻고 답을 어느 파일 어느 자리에 쓰는지만 갖는다.

**`init`은 첫 loop다.** `make loop --type plan`으로 열고, 정본 지식을 세우다 첫 milestone을 자르면 닫힌다. 자를 것이 아직 없으면 열린 채 남고 그것이 정상이다. 어느 답이 사람의 것이고 어느 것이 추천 채택인지는 loop의 `Dialogue`가 담고, 재개는 `loop` skill이 열린 loop를 보는 것으로 된다.

### loop — plan 축의 사이클

REAP는 기획을 쓴다. 쓰는 단위가 loop이고(`02-flow.md`의 `plan 축의 단위는 loop다`) 그것을 다루는 skill이 `loop`다. `carve-milestone`과 **대상이 다르다** — `loop`는 plan source에 쓰는 일이고 산출은 plan 문서(또는 설계·화면·idea)다. `carve-milestone`은 이미 있는 plan을 읽어 milestone으로 자르는 일이다. 한 loop가 둘 다 하는 것이 보통이다.

`loop` skill이 판단하는 것은 여덟이다. 앞의 둘은 여닫기, 나머지 여섯은 한때 `author-plan`이 갖기로 했던 것이다.

**0. 새 loop인가 이어갈 loop인가.** 여럿이 열려 있으므로 먼저 `life/loops/`를 본다. 같은 물음을 다루는 loop가 열려 있으면 거기 잇는다 — 새로 열면 논의가 두 기록으로 갈라진다. 유형은 산출물이 갈 자리로 정한다.

**0'. 닫을 때가 됐는가.** 산출물이 자리를 찾았는가 — plan source에 썼거나, milestone을 잘랐거나, `idea/`에 남겼거나. 그러면 `mark loop --closed`. 닫힌 loop는 `life/loops/`에 남아 그 milestone을 실행하는 세대가 읽는다(10개 초과분만 도구가 archive로 내린다). 못 찾았으면 열린 채 두고 `Dialogue`·`Dead Ends`를 적어둔다.

**1. 어느 소스에 쓸 것인가.** 여러 소스가 role을 달리해 등록돼 있다. 잘못 고르면 같은 주제의 자료가 두 곳으로 흩어지고, 흩어진 자료는 어느 쪽도 완전하지 않다.

**2. 규약을 먼저 읽는다.** `conventions/<ps-id>-<slug>.md`를 읽고 그 소스의 구조·형식·관례에 맞춘다. **REAP는 그 소스를 소유하지 않는다.** 그 소스의 규칙이 REAP의 취향보다 우선한다.

**3. 새로 쓸 것인가, 기존을 고칠 것인가.** 기획 문서는 쌓이면 서로 모순된다. 고쳐야 할 문서가 있는데 새로 만들면 두 개의 진실이 생기고, 다음 세션은 어느 쪽이 맞는지 알 수 없다. 쓰기 전에 그 주제를 이미 다룬 문서가 있는지 찾는 것이 첫 동작이다.

**4. 규약 자체를 갱신한다.** 소스를 다루며 알게 된 것 — 어디에 무엇이 있는지, 이 소스가 새 문서를 어떻게 받는지, 하지 말아야 할 것 — 을 `conventions/`에 되먹인다. **이것이 "REAP가 plan source를 기억한다"는 말의 실제 내용이다.** 이 되먹임이 없으면 규약 문서는 등록할 때 사람이 쓴 두 줄에서 영원히 멈춘다.

**5. 아직 결론이 안 난 것은 plan에 쓰지 않는다.** `idea/research/`로 보내거나 `idea` loop로 남긴다. 모호한 것을 단단한 자리에 두면 단단해 보이고, 다음 세션이 그것을 결정된 것으로 읽는다.

**6. 커밋 규칙이 이 소스에 적용되는가.** plan source는 리포 밖일 수 있고 git이 아닐 수도 있다. git 리포라면 그쪽 커밋도 loop를 닫는 조건이 되고, 아니라면 적용되지 않으며 **적용하지 않았다고 말한다.**

**`Dialogue`를 남긴다.** loop가 도는 동안 사람과 갈린 지점 — 무엇을 물었고, 선택지가 무엇이었고, 사람이 무엇을 골랐고, 추천 채택인지 다른 답인지. 전사가 아니다. 이것이 없으면 다음 세션이 같은 것을 다시 묻거나, 사람이 고른 것을 agent가 정한 것으로 읽는다.

**규범을 옮겨 적지 않는다.** 정한 것은 plan source에 쓰고, loop 기록에는 *왜 그렇게 정했는가*와 *접은 길*만 남는다. 기록에만 있는 결정은 안 정해진 것이다.

### evolve의 첫 판단 — 세대를 열 값이 있는가

축보다 먼저 오는 질문이다. **한 번의 편집과 한 번의 커밋으로 끝나는 일은 세대가 아니다.**

근거는 기록의 존재 이유다(`04-commands.md`의 *기록이 세대가 도는 동안에도 쓸모 있어야 하는 이유*). 기록이 하는 일은 **도는 동안 "무엇을 하려던 중이었나"를 붙잡는 것**이고, **한 번에 끝나는 일에는 도는 동안이 없다.** 값 없이 열면 기록 파일·레지스트리 행·닫는 커밋만 남는다.

**작아도 세대인 것 셋.** backlog 항목을 소비할 때(`consumedBy`가 바인딩된 세대를 받으므로 **구조가 요구한다**), 접은 접근이 있을 때(커밋은 한 것을 담고 안 한 것은 안 담는다), 다른 세션이 함께 돌 때(상태 줄이 진행 중임을 알리는 유일한 수단이다).

**애매하면 열지 않는다.** 세대는 일 도중에도 열 수 있고, 열어둔 것을 되돌리는 쪽이 더 비싸다.

**이 판단을 `doctor`가 검사하지 않는다.** 세대 밖 커밋은 어긋남이 아니다 — 검사하는 것은 "커밋 없이 닫힌 generation"이지 "세대 없이 한 커밋"이 아니다.

### evolve의 둘째 판단 — 어느 축인가

열기로 했으면 유형을 정한다. **그 전에 한 갈래가 먼저 빠진다 — 새 의도를 만드는 일이면 generation이 아니라 loop다.** `evolve`는 거기서 `loop` skill로 보내고 자기는 열지 않는다.

**한 질문으로 갈린다.**

| 이 일은 | 어디로 | 근거 |
|---|---|---|
| 새 의도를 **만드는가** | **`loop`** (generation이 아니다) | 선택 — 출처일 뿐 |
| 새 의도를 **실현하는가** | exec generation | **필수 — milestone 또는 backlog 항목**(`02-flow.md`) |
| 이미 있는 의도로 **되돌리는가** | fix generation | 없음 |

**loop와 exec 사이의 기본값은 이렇다.** 지금 착수 가능한 근거가 있으면 execute, 없으면 loop. 이것은 기본값이지 규칙이 아니다 — 착수 가능한 항목이 있어도 그것이 지금 필요와 맞지 않으면 loop가 맞다. **fix는 이 기본값과 무관하다** — milestone이 열려 있든 아니든 되돌리는 일은 fix다.

**loop로 보내야 하는 신호**

- 무엇을 만들지가 아직 서지 않았다. 요청이 "무엇을 할지"보다 "무엇이 필요한지"에 가깝다
- 열린 milestone이 없거나, 남은 것이 지금의 필요와 맞지 않는다
- `idea/research/`에 결론이 안 난 조사가 쌓여 있고 그것이 방향을 막고 있다
- 직전 execute 세대가 "계획이 부족해서" 막혔다

**execute 축을 골라야 하는 신호**

- 착수 가능한 milestone이 있고, 그 안에 남은 일이 명확하다
- backlog 항목 하나가 무엇을 할지를 이미 다 적고 있다
- 필요한 판단이 이미 spec에 있다

**fix 축을 골라야 하는 신호**

- 만들어둔 것이 의도대로 돌지 않는다 — 버그, 깨진 빌드, 낡은 의존성, 오타
- 되돌아갈 곳을 지목할 수 있다. 지목할 수 없으면 그것은 fix가 아니다

**세 가지 안티패턴을 이름 붙여 경계한다.**

*계획이 부족한 줄 알면서 밀어붙이기* — execute 축에서 "일단 해보면 알겠지"는 대개 loop를 열어야 한다는 신호다. REAP에서 planning 단계의 잘못된 가정이 구현까지 흘러가 마지막에 발견되던 것이 이것이다.

*plan을 핑계로 실행을 미루기* — 반대 방향의 실패다. 기획은 무한히 정교해질 수 있다. loop는 열린 채 두는 것이 허용되지만, **어느 loop도 milestone을 못 낳은 채 열린 loop만 쌓이면** 그것이 신호다.

*작다는 이유로 새 기능을 fix로 짓기* — fix의 기준은 크기가 아니라 **되돌리는가**다. 작은 새 기능은 fix가 아니라 exec이며, 근거가 필요하다. 근거는 backlog 항목 하나면 되므로 비싸지 않다. 이 구멍을 막지 않으면 세 번째 유형이 milestone 규율을 우회하는 뒷문이 된다.

**애매하면 `interview`를 먼저 부른다.** 축을 잘못 고르는 것은 세대 하나를 통째로 낭비하는 일이고, 그것을 막는 데 드는 질문 두세 개는 싸다.

## interview — 모호성을 제거하는 독립 절차


REAP에는 모호한 의도를 구체화하는 절차가 없었다. 한 줄짜리 요청을 agent가 추측으로 확장하고, 그 추측이 구현까지 그대로 흘러가 마지막에야 발견된다. 무엇이 범위 밖인지 어디에도 남지 않아 다음 세션이 다시 추측한다.

REAP에서 이것은 **독립 skill**이다. 어느 명령의 내부 기능도 아니다. 모호성은 세대를 열 때만 생기지 않고 plan을 쓸 때도, milestone을 자를 때도, 접근을 고를 때도 생긴다. 한 곳에 묻으면 나머지에서 다시 만들어야 하고, 같은 규율을 네 곳에 복사하는 순간 그것은 carrier 문제가 된다. **규율의 소유자는 한 곳이다.**

사용자가 직접 부를 수도 있고, 다른 skill이 "먼저 이것을 하라"고 가리킬 수도 있다. 가리키는 쪽은 **호출 지시만** 갖고 규율 본문을 갖지 않는다.

### 목적

사용자의 모호한 개념을 **구체화하고, 기록으로 남기고, 착수 가능한 형태로 만든다.** 그 셋이 설 때까지 집요하게 묻는다.

### 질문 형식

"집요하게 묻는다"와 "사람의 인지 능력을 고려한다"는 긴장 관계다. 해소 방법은 질문에 관대해지는 것이 아니라 **사람에게 갈 질문의 수를 줄이는 것**이다. 코드와 문서로 답할 수 있는 것은 agent가 스스로 확정하고, **판단이 필요한 것만 사람에게 간다.**

1. **한 번에 질문 하나.** 묶어 던지면 앞부분만 답하고 뒤를 흘린다.
2. **선택지 2~4개 + 자유 입력.** 다섯 개를 넘으면 비교 자체가 부담이다. 자유 입력은 항상 열려 있어야 한다 — 선택지는 사고를 돕는 장치이지 가두는 장치가 아니다.
3. **각 선택지에 "고르면 무슨 일이 생기는가"를 한 줄로.** 이름만으로는 비교할 수 없다.
4. **추천안을 맨 앞에 두고 근거를 한 줄로.**
5. **"모르겠다"는 막다른 골목이 아니다.** 추천안을 채택하고 그 사실을 기록한 뒤 진행한다. 되묻지 않는다.
6. **끝이 보여야 한다.** 남은 모호성 개수를 함께 보여준다. 언제 끝날지 모르는 질문은 사람을 이탈시킨다.

**추천의 함정.** 모든 질문에 추천을 붙이면 사용자가 추천만 누르게 되고, 그러면 interview는 형식만 남고 모호성은 그대로 남는다. 따라서 추천은 **근거가 있을 때만** 붙이고, 근거는 코드·genome·기존 결정에서 나와야 한다. **취향과 우선순위를 묻는 질문에는 추천을 붙이지 않는다** — 그것은 사람이 결정해야 하는 것이고, 추천은 그 결정을 대신해버린다. 추천이 채택됐는지 사용자가 다른 답을 냈는지를 기록에 남긴다. **전부 추천으로 채워진 산출물은 interview가 작동하지 않았다는 신호다.**

### 진행 규율

| 규율 | 무엇을 막나 |
|---|---|
| 코드가 답할 수 있는 건 묻지 않는다 | 사람의 인지 부하. 확정 가능한 사실은 확정한 뒤 "확인" 형태로 제시 |
| 질문 전에 기존 구조와 최근 커밋을 본다 | 발견형 질문("X 있나요?") 대신 확인형("X를 봤는데 Y로 가정할까요?") |
| 모호성 대장(ledger)을 병렬로 추적한다 | 한 세부 주제가 나머지를 밀어내는 것. 몇 라운드마다 재방문 |
| 자문자답이 3회 연속되면 다음은 반드시 사람에게 | agent가 혼자 결론내는 것 |
| 자유서술 답변은 구조화해 되읽어주고 확인받는다 | 범위·제약·결정이 담긴 답변의 오독 |
| 종료 직전 한 문장으로 압축해 명시 승인 | 승인 없는 종료 |
| 접근안 2~3개와 그 대가를 제시한다 | 첫 안에 갇히는 것 |
| YAGNI | 모든 안에서 불필요한 기능 제거 |

### 종료 조건

**agent가 "충분히 물었다"고 스스로 끝내지 않는다.** 아래가 서지 않으면 종료하지 않는다.

1. 문제 진술이 **관찰 가능한 형태**인가 — 재현 조건 또는 근거
2. **완료 판정 기준**이 있는가
3. **범위 밖**이 명시됐는가
4. 미결 결정이 **열린 항목으로 기록**됐는가
5. 다음 세대가 **그대로 착수 가능한 수준**인가

사용자가 "그만"이라고 하면 즉시 종료한다. 단 **미해결 모호성을 버리지 않는다** — 기록의 Open Questions로, 또는 `idea/`로 남긴다. 조용히 끝내면 추측이 다시 시작된다.

### REAP에서 달라진 것

REAP 설계안은 이것을 `config.interview` 플래그로 켜고 끄고, `clarity` 판정과 maturity 비율에 연동하려 했다. **REAP에는 그 축이 전부 없다.** 흐름을 판단하는 것이 skill의 일이므로, 언제 깊게 묻고 언제 한두 문장으로 확인만 할지는 skill 자신이 기술한다. 설정 플래그는 두지 않는다 — 판단을 config로 빼는 것은 판단을 스크립트로 빼는 것과 같은 실수다.

호출 지점도 명령이 아니라 skill이다. `evolve`와 `carve-milestone`이 각각 "의도가 모호하면 `interview`를 먼저 하라"고 가리킨다.

**클라이언트 의존성.** Claude Code에는 선택지 UI를 가진 질문 도구가 있다. skill은 그것에 의존하지 않는다 — 있으면 쓰고, 없으면 번호 붙인 선택지를 평문으로 제시한다. 형식(선택지 + 자유 입력 + 추천)은 어느 쪽이든 같아야 한다.
