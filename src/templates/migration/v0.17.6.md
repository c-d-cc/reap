# v0.17.6 — the daemon is gone; the indexer is built in

REAP no longer ships a resident process. `@c-d-cc/reap-daemon` is retired
(deprecated on npm), and the code index now lives inside `reap` itself.

Nothing here is urgent. `reap` works unchanged if you do nothing; these steps
remove settings that stopped meaning anything and data nothing reads.

## 1. `config.yml` — `daemon` and `daemonBin` are no longer valid

If your `.reap/config.yml` contains either field, **`reap update` has already
removed it** by the time you read this — it prunes fields that are no longer
valid and reports the removal in its output.

That is the intended outcome, not a loss. There is no resident process to enable
and no binary to point at. The index is built by `reap index` and refreshed by
the commit at the end of each generation.

**No action needed.** If you kept a copy of your config, do not restore either
field: `reap update` will remove it again.

## 2. `~/.reap/daemon/` — removed for you

The daemon kept a registry of indexed project paths and one SQLite symbol graph
per project under `~/.reap/daemon/`. Nothing writes or reads it now, and
`reap update` deletes the directory.

**No action needed.** Only that one entry is touched — anything else you keep in
`~/.reap/` is left alone.

## 3. If you installed the daemon package globally

Check and remove it:

```bash
npm ls -g --depth=0 @c-d-cc/reap-daemon   # is it there?
npm uninstall -g @c-d-cc/reap-daemon      # if so
```

`reap uninstall` also names it, so you do not need to do this by hand unless you
are staying and simply want the disk back.

**Kill a stray process if you have one.** The daemon stayed resident for thirty
idle minutes and, in at least one observed case, survived as an orphan its own
`reap daemon stop` could not find:

```bash
lsof -iTCP:17224 -sTCP:LISTEN    # nothing should answer
```

## 4. What replaces it

```bash
reap index status               # counts, import resolution rate, indexed commit
reap index search <query>       # find a definition
reap index impact <file>        # what breaks if you change this file
reap index callers <symbolId>   # symbolId looks like src/core/lifecycle.ts::fn
```

There is nothing to start. Queries refresh the index themselves when `HEAD` has
moved, and the generation's commit refreshes it eagerly.

The index is written to `.reap/.index/` in each project — **not** to your home
directory. **`reap update` adds it to `.gitignore` for you**, which is why this
step needs nothing from you beyond having run `reap update` once.

It appends only when no line already names that directory, so if you had
already ignored it yourself nothing changes. A *broader* rule you may have —
`.reap/` on its own — is not recognised, and you will get a redundant entry.
Harmless, and you can delete it.

Committing the index would mean the commit containing it has to be indexed,
which is a loop — and `reap run completion --phase commit` runs `git add -A`,
so an unignored index would be committed on every generation.

## 5. One behaviour worth knowing

**The index is keyed by commit.** Symbols you have written but not committed are
not in it. `reap index status` always shows which commit the index describes, so
you can see when that matters. Use ordinary search for uncommitted work.

If you use `daemon: true` in a project that also pinned a REAP version below
0.17.6, nothing breaks — the old code simply finds no daemon, which is what it
already did.

## 6. `genome/evolution.md` — a new rule about `environment/source-map.md`

`environment/summary.md` is loaded into the agent's context every session.
`environment/source-map.md` is **not** — it is on-demand, so an agent only reads
it if something tells it to. Nothing did, which meant the file could describe a
codebase in detail and never be opened while that codebase was being changed.

0.17.6 adds a rule to the genome REAP ships. Your `genome/evolution.md` is
yours, so `reap update` does not touch it — this section is the only way the
rule reaches a project that already exists.

**This is the one step here that needs you.** Sections 1 to 5 were done for you.

### If your `## Code Quality Principles` section looks exactly like this

This is what 0.17.5 and every earlier version shipped, unchanged since 0.16.0.
Compare it against yours **including the intro sentence and every bullet**:

```markdown
## Code Quality Principles

Before writing new code, always read existing code first to understand established patterns.

- **Pattern-first**: Identify how existing code with the same role is structured. New code must follow that pattern.
- **Consistency over preference**: Codebase consistency takes priority over personal preference. If a better pattern exists, refactor all instances — don't introduce a second pattern alongside the first.
- **No duplication**: The same logic must not exist in two places. Extract and share when duplication is found.
- **Verify before commit**: Before committing, verify new code matches existing patterns and contains no duplication.
- **Enforced conventions in application.md**: Deliberate design decisions that cannot be derived from code alone (especially when violations exist in the codebase) should be recorded in application.md. When stated, application.md conventions take precedence over the current state of the code.
```

If it matches, **replace it with this and say nothing** — you are restoring a
file to the state it would have had if the project were initialised today, and
asking permission to do that turns a no-op into an interruption:

```markdown
## Code Quality Principles

Before writing new code, always read existing code first to understand established patterns.

- **Read source-map first**: open `environment/source-map.md` before changing code. `summary.md` is loaded automatically; source-map is **on-demand**, so unless you open it you are editing modules whose role and ownership you have never seen. `reap index` answers what calls what — it cannot answer why a module is shaped the way it is. `reap init` writes this file. If a project has none — it was initialised before REAP wrote one — read whatever structure `summary.md` carries instead, and write a source-map the first time you need to describe the code's shape.
- **Pattern-first**: Identify how existing code with the same role is structured. New code must follow that pattern.
- **Consistency over preference**: Codebase consistency takes priority over personal preference. If a better pattern exists, refactor all instances — don't introduce a second pattern alongside the first.
- **No duplication**: The same logic must not exist in two places. Extract and share when duplication is found.
- **Verify before commit**: Before committing, verify new code matches existing patterns and contains no duplication.
- **Enforced conventions in application.md**: Deliberate design decisions that cannot be derived from code alone (especially when violations exist in the codebase) should be recorded in application.md. When stated, application.md conventions take precedence over the current state of the code.
```

### If it already mentions `source-map`

Nothing to do. Do not report it, do not ask — this project is already there.

### If it is anything else

Your genome has been edited or translated, and this note cannot know which parts
were deliberate. **Show the human the one bullet being added and ask before
writing.** If they decline, leave the file alone and **do not run
`reap update --mark-migrated`** — leaving it unmarked is what makes this note
come back next session rather than disappearing unapplied.

Translate the bullet into the language the rest of that file is written in. A
rule in the wrong language is a rule the agent reads past.

### And then: does the file the rule names actually exist?

Check `.reap/environment/source-map.md`.

- **`reap init --mode adoption`** has always written it from a scan of your code.
- **`reap init` on an empty directory (greenfield)** did not, until 0.17.6.

So if your project started as greenfield, the rule you just installed points at
nothing. Write the file: read the codebase and record what each module or
directory is for and what owns it — the part `reap index` cannot tell you.
`environment/summary.md` may already carry a structure section; if so, move it
here and leave a pointer, which is what keeps summary.md from growing with the
file count.

Do not leave an empty file behind instead. A source-map that says nothing is
worse than an absent one, because the rule stops the agent at a file that
answers nothing rather than sending it to `summary.md`.

## 7. The other half of the same file: where structure gets *written*

Section 6 gave your agent a rule about **reading** `environment/source-map.md`.
Your `genome/evolution.md` still says the reflect phase maintains the structure
description in **`summary.md`** — so the two halves point at different files, and
whichever one the agent follows, the other is wrong.

Fix them together. This is the same file and the same edit session as section 6.

### `## Environment Refresh at Completion`

The shipped original — one bullet is wrong now, the rest is unchanged:

```markdown
- Primary update targets: Tech Stack, Source Structure, Tests sections
```

Replace that single line with:

```markdown
- `summary.md` — Tech Stack, Tests, and anything else loaded every session
- `source-map.md` — the code's structure: modules added or removed, and what each is for. Whichever file holds your structure description is the one to update; do not maintain it in both
```

And the line above it, `Incrementally update environment/summary.md during reflect
phase:`, becomes `Incrementally update environment/ during reflect phase:` — it
now names two files, not one.

### `## Genome vs Environment Boundary`

The shipped original:

```markdown
- **environment (summary.md)**: descriptive — "how things currently are" (tech stack, source structure, build, tests, dependencies). When code changes, only environment is updated.
```

Replace with:

```markdown
- **environment (`summary.md`, `source-map.md`)**: descriptive — "how things currently are" (tech stack, structure, build, tests, dependencies). When code changes, only environment is updated. `summary.md` is loaded every session, so keep it from growing with the file count; `source-map.md` is on-demand and is where the structure description belongs once it is large enough to matter.
```

### Same three-way judgment as section 6

Exact match with an original above → **edit silently**. Already mentions
`source-map` → **no-op, say nothing**. Anything else — edited, translated,
reorganised → **show the human the change and ask**, and if they decline, leave
it and do not run `reap update --mark-migrated`.

Translate into whatever language the rest of the file is written in.

### Why this is not cosmetic

Without it, a project that follows section 6 ends up with a rule telling its
agent to read a file that the reflect phase is never told to write. The structure
description keeps growing in `summary.md` — which is loaded into context every
single session — while `source-map.md`, the file the agent is sent to, says
nothing. That is the state section 6 itself calls worse than an absent file.

**What this note does not settle**: which file *should* own the structure
description in your project. Both are yours. The rule above only says that the
one holding it is the one to keep current, so the two halves stop contradicting
each other.
