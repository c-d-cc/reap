# v0.17.5 — Add the evidence-kind rule to genome/evolution.md

## What changed in REAP

REAP now asks agents to record **what kind of evidence** stands behind each verification claim, instead of writing "verified" for everything. The rule ships in `src/templates/evolution.md`, so new projects get it from `reap init` — but **REAP never overwrites an existing project's genome**, which is why this note exists.

The rule came out of two consecutive REAP generations in which the same failure appeared:

- gen-083 recorded an item as satisfied that nothing had actually executed. An independent evaluator caught it while every test was green.
- gen-084 adopted a tagging convention to prevent exactly that, and then failed **one row over** — the behaviour under test was correct, but no command in the gate or the suite exercised it.

"It was correct" is not an answer to this problem. A claim nobody ran is unverified whether or not it happens to be true.

## Genome immutability — a deliberate, one-time exception

Normally the genome changes only during `completion --phase adapt`. **This note is an explicit exception, limited to v0.17.5**, because the rule concerns how agents write artifacts in every generation and cannot wait for one. Do not treat it as a precedent.

## Required actions for the AI agent

### 1. Decide which of three cases your project is in

Open `.reap/genome/evolution.md` and search for `Record what kind of evidence` (English) or `검증 근거는 종류를 구분해` (Korean).

| Case | What you find | Action |
|---|---|---|
| **A** | The section is already present | **No-op.** Do not ask the user anything. Skip to step 3 |
| **B** | Absent, and the file otherwise matches what REAP ships | Add the section silently (step 2), then step 3 |
| **C** | Absent, and the file has been edited or translated by the user | Show the user the text you propose to add and **ask before writing**. If they decline, stop and do **not** run `--mark-migrated` |

Case C exists because a user-authored genome is theirs. Adding text to a document someone rewrote is a change they should see.

### 2. Add the section

Insert it directly **after** the section on testing principles / building checks (the one ending with a line about recording what a check cannot see), and **before** the architecture-sync section. Write it in the project's configured language (`.reap/config.yml` → `language`); the English original is below.

```markdown
### Record what kind of evidence you have — and "ran it" must name the command

Writing only "verified" in an artifact makes **running the command and reading the code look the same.** That distinction collapsed in two consecutive generations, and a blocking defect came through each time.

Tag every item with the kind of evidence behind it:

- `[ran]` — this generation executed that command
- `[negative]` — broke it on purpose and watched the check fail
- `[read]` — judged by reading the code. Not executed

**To write `[ran]`, you must be able to name the command that exercises that item.** If you cannot, it is `[read]`.

When unsure, run `grep -rn "<functionName>" tests/`. Zero hits means `[read]`.
```

Keep the tag names in whatever form your artifacts already use if you have an established convention — the point is that the three kinds are distinguished, not the exact spelling.

### 3. Check the size guideline

`genome/evolution.md` has a ~300-line guideline. If this addition pushes past it, do **not** delete text to get under the number — that is how true statements get lost. Report it to the user and let the next `completion --phase adapt` decide what belongs elsewhere.

### 4. Mark the migration applied

Only after every pending note is handled:

```bash
reap update --mark-migrated
```

If you skipped step 2 in case C, do **not** run this — the note should surface again next session.

## Also in v0.17.5 — action only if you use the daemon

The code-intelligence daemon is now a separately published npm package (`@c-d-cc/reap-daemon`). It was documented from v0.16 but never published, so `daemon: true` could not work on an npm install.

**If and only if your project sets `daemon: true` in `.reap/config.yml`**, install it once:

```bash
npm i -g @c-d-cc/reap-daemon
```

REAP and the daemon are separate packages and locate each other only when they share a resolution root. If yours do not — a global REAP with a project-local daemon, two package managers, a Node version switch — set `daemonBin` in `.reap/config.yml` or `REAP_DAEMON_BIN` for a single command. `reap daemon status` reports where it resolved from.

Projects without `daemon: true` need to do nothing; the flag defaults to off and the lifecycle is never blocked either way.
