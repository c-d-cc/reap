# Longterm Memory

> Design lessons that prevent future generations from repeating mistakes. If a lesson is already in genome (application.md / evolution.md), it does not belong here. Bloat = pruning was skipped.

## Architecture Patterns

- **CLI-driven flow, minimal slash commands**: a single slash command + CLI emits "what to do next" on stdout (ping-pong). Avoid per-stage slash commands.
- **Static template + dynamic context**: agent definitions (`reap-evolve.md` etc.) are static — role/mindset/behavior only. Dynamic generation state goes through `buildBasePrompt()`.
- **Single source when format matches**: if two adapters accept the same file format (e.g. Claude Code skills + OpenCode slash commands), keep ONE source dir. Split only when client-specific frontmatter is needed.
- **Termination paths live outside the transition graph**: abort / early-close are explicit `state.stage` guards, not graph edges. New escape paths copy abort.ts/early-close.ts pattern.
- **Nonce-graph external CLI = state side-channel**: append-only state writes (e.g. `report-evaluator`) bypass nonce graph and use plain state appends. Don't pollute the graph.
- **Destructive-action safety belongs in structure, not flags**: to guarantee a check never deletes user data, put it only in the read-only path (`checkIntegrity`) and add nothing to the mutating one (`fixProject`). A conditional saying "don't delete" can be flipped later; an absent code path cannot.
- **A rule the agent must follow lives in the phase prompt, not only in the guide**: guides load early and compete with everything else in context; the phase prompt is read at the moment of action. Every behavioral rule needs a carrier at the point of use.

## Design Heuristics

- **Design docs survive abort and anchor future generations**: when aborting, consciously decide whether to preserve the `vision/design/<topic>.md`. If preserved, an aborted track can resume cleanly many generations later.
- **When a sentence is the defect, delete it rather than annotate it**: reap answered a failed push with "check remote configuration and network" while git had already written the exact command to run and reap discarded it — and on the day it mattered both named causes were fine. Attaching the real cause beside the guess keeps the guess, and a guess phrased as a diagnosis is what sends people looking in the wrong place. The user reads the message, not the context field.
- **Self-dogfooding timing is deliberate**: activate a new opt-in flag at the lifecycle stage where the same generation will be its first user (e.g. enable `evaluator: true` at end of implementation so validation is first user).

## Anti-patterns

- **Subagent calls as lifecycle gates**: an environment may lack Agent (Task) tool. Always advisor + fallback, never gate.
- **Cross-asset path helpers that trust the module's apparent location**: bundling collapses every module into one file, so a helper's depth from the package root changes and the bare `__dirname` becomes a *build-time string literal* — a published bundle carried the build machine's absolute path for three generations. Resolve from `import.meta.url`, and prefer placing the helper where source and bundle depths coincide over branching on them correctly.
- **A whole-graph computation whose result is *added* rather than *replaced***: resolving calls or imports matches against the current symbol set and the current file list, so the previous answer for an untouched file can be wrong now. gen-089 applied "replace, not append" to one of two edge kinds and shipped the other; earlier in the same generation the omission ran the other way and five ordinary commits emptied the call graph. If a computation reads everything, redo it over everything and drop what it produced last time.
- **A cache cannot know whether the work it records actually happened**: an install stamp turned four installers that each swallow their own failures into a permanent loss — a settings file that would not parse produced "synced", and nothing retried at that version. The swallowing predated the stamp; what the stamp added was finality. Anything that records "done" has to be handed evidence of what landed, not the fact that a call returned — and typing the return `unknown` is how you foreclose that.
- **`YAML.parse → mutate → stringify` for user-authored frontmatter**: round-trip loses comments, key order, quote style, numeric inference. Use YAML.parse for *analysis only*; write with line-level manipulation.

## Process Heuristics

- **Check, don't reason about it**: `grep -rn "fnName"` before deciding when something is called; a one-minute repro before trusting a framework's semantics (CLI parsing, library edge cases). This holds even when your conclusion is right — gen-077 correctly judged "the test is stale", then found a separate bug only by splitting that test into a case per code path. A correct diagnosis still has blind spots. **A failure mode named after a tool is a hypothesis: install the tool and measure before writing it down.** gen-083 recorded "pnpm and Yarn PnP cannot resolve this, in principle" under the heading *known breakage, not unverified* — obeying the rule to say what breaks while never testing that claim, so the form of certainty stood in for the measurement. Both resolve fine; what breaks is unrelated to the manager. And the first attempt to measure it was itself wrong, so re-measure the way the real code asks, not the way that is convenient. And the same applies to a *consequence*: gen-085 correctly identified which functions shared a broken comparator, then described a behaviour change that could not occur — one of them returns on `-alpha` long before it compares. The mechanism was right and its reach was invented.
- **A verification claim is a claim — about the check and about what passing it proves**: gen-084 wrote two that were plausible and unchecked ("typecheck will catch the missing fixture fields" — it only compiles `src/`; "run the gate before building to watch it fail" — the gate builds first). Then the other half: skipping the new behaviour to make an old test green leaves it permanently unverified, and a perfectly deterministic verdict can still measure the wrong thing — gen-079's layer-2 check judged by a file appearing on disk and passed with every slash command deleted, because the agent fell back to the CLI and produced the same file. Run the check the plan names, and ask what its passing observes — and when a negative test goes red, read WHICH tests. gen-085 justified a policy by "revert it and three tests go red" — all three were tests it had just written for that policy, and no pre-existing test broke. The policy was right and kept, on a reason it had not yet given: the repository has a script that publishes the prereleases in question. A conclusion resting on an unexamined reason is the dangerous kind, because the reason is what gets reused. **Changing a check's environment creates conditions as well as removing them**: gen-088 put the target prefix on PATH so the gate would stop testing the published package, and thereby armed an auto-update that a missing binary had been accidentally suppressing — every future release would have gone red at the gate that runs before publish. Ask what newly becomes true, not only what stops being false.
- **A suite that has only ever run on one machine is measuring that machine**: gen-081 pointed CI at a green suite and three latent bugs surfaced at once — missing git identity, a branch name inherited from `init.defaultBranch`, and a `mock.module` stub reaching every file loaded after it. The third passed on macOS and failed on linux purely from directory walk order, so "it passes locally" had been evidence of nothing. Green on one environment is a sample of size one.
- **Reproduce the environment before trusting the reproduction**: the container chosen to imitate the runner had no git installed, so it produced a different failure that nearly confirmed the wrong cause. A repro that differs from the target in an unchecked way adds a variable rather than removing one.
- **You cannot measure a variable's effect in an environment that lacks it**: gen-082 measured that opencode honours `$HOME`, correctly, and drew the wrong conclusion — the developer machine had no `XDG_CONFIG_HOME`, so "follows HOME" and "falls back to HOME when XDG is absent" were indistinguishable. REAP had been writing where the client does not look for anyone who sets it, silently. Set the variable to something visible and re-measure before concluding it does not matter.
- **Test isolation must cover every axis the process reads**: external tools need a port axis and a path axis — either alone leaks into the user's environment. For paths, enumerate what the process actually consults rather than the one variable you thought of: faking `HOME` while inheriting `XDG_CONFIG_HOME` left a dozen tests writing into the real config directory. And an env override only reaches a *spawned child* — bun's `os.homedir()` ignores `$HOME` in-process (node's follows it), so inject the directory instead. And rank risk cheaply rather than confidently: the same generation called native-dependency daemon tests its highest risk and unit tests its lowest, exactly inverted — adding one suite per run cost nothing and made each failure self-attributing anyway.
- **Naming one cause for an absence is the mirror of asserting the absence, and it is the half people believe**: the release gate confirmed a missing file correctly and then said which REAP defect it was — while the agent's own reply, printed two lines below, said the opposite. `A → B` was written in the comment and `B → A` was what ran. A gate that answers only pass/fail has nowhere to put "the agent never reached REAP", so it puts it under fail, and a wrong red at every release teaches people to scroll past a check that will one day be right. Enumerate causes, or add a third answer — and draw the line by *which side of it is about your project*, not by which failures feel excusable. Then: **removing a cause exposes what that cause was incidentally blocking** (opening permissions made the CLI bypass easier, so the bypass negative had to be re-run), and **the reasoning that decides is not the only thing that can be wrong** — two of four review rounds landed on the line a human reads, where the count asserted evidence the printed entry no longer contained, first by ordering, then by truncation. Each fix's own subject was where the next defect lived.
- **A substring chosen to mean "relevant to us" can select adversely**: filtering permission denials for `reap` looked conservative until the review asked what an agent that *cannot find* the slash command actually does — it says reap more, not less (`ls ~/.claude/commands | grep reap`, and the project's own domain is reap.cc). The string most likely to appear in the exact scenario the check exists to catch would have been the string that excused it. Pick the token the working path emits (`reap run`), and re-read every sentence about the value when you narrow it — a carrier marker says "here too", never "you just changed this", and four carriers planted one round earlier went stale inside the generation that planted them to prevent exactly that. Widening a match from one token to two also quietly falsifies "this depends on no field shape": two tokens assume adjacency.
- **An assertion of absence has to prove itself first**: "the warning is gone" is indistinguishable from a crash, unparseable output or a renamed field, so it passes for reasons that have nothing to do with the fix. Its mirror — "the warning is present" — is self-proving, since nothing can be found in output that was never produced. Demand evidence the command ran (a status, a numeric count) before reading anything into silence. The same care applies to writing the check itself: `cmd | grep -q` under `set -o pipefail` reports the *upstream* failure caused by grep's own early exit, so a match becomes a pass — found only by running the negative test on the newly written assertion. And a negative that comes back *green* is the same finding one level up: gen-088 disabled the very bypass its test existed for and the test passed, because a reinstall would have been deleted again a line later — end states matched. Key on something only one branch can produce (a directory the reinstall recreates; the three seconds a spawn attempt costs), and run the negative on the single test, not the file — elsewhere in that file another test went red and hid an assertion that was inert.
- **A check that binds two artifacts has to say WHERE, and then say what is holding it closed**: a migration note carries two renditions of the same text — the original to compare against and the one to install — so `note.includes(shipped)` is satisfied by the *wrong* one, leaving the install block stale and the comparison block wrong while green. Extract and compare by position, with equality. Then the second half, which is the part that gets missed: after fixing a helper to fail closed, name the assertion that now rejects the bad value and re-run the attack with that assertion deleted — an empty block still passed the count and the equality, and only a `toContain` loop written for another purpose was holding the door. And a negative guard on a string is usually a proxy: `not.toContain("no source files yet")` catches the one sentence you thought of, while the property was "this text was written without looking at the tree", which is directly assertable.
- **Verify the backlog's claims, don't just execute them**: a backlog is a snapshot of one investigation and can be wrong (gen-073's said RELEASE_NOTES was stale; it wasn't — the header scan had missed what `## What's New` meant). High clarity means act decisively, not accept premises unchecked.
- **The generation that corrects a defect is the likeliest to repeat it**: gen-083 fixed a false coverage claim, a value two places knew differently, documentation contradicting the code, a silence indistinguishable from success, and a bun-only path nobody had exercised — then shipped every one of those shapes itself, inside the very checks written to end them. Being mid-repair confers no immunity; ask separately whether you are reproducing the shape you are removing.
- **An independent reviewer earns its cost when every check is already green, and the rounds do not converge on their own**: gen-083 got four blockers over two rounds that way. gen-089 needed *three* rounds — and every round after the first found its defects **inside the previous round's repair**: a check that failed open in the direction it guarded, an assertion that could not fail, and "replace, not append" applied to one of two symmetric cases. Budget for the second and third pass rather than treating the first as the audit.
- **The neighbourhood of each fix is where the next defect lives**: four review rounds on one script, every one of them landing inside the previous round's repair — the fail-open analysis that covered one of two paths, the substring that then selected adversely, the carrier marker that went stale *in the generation that planted it to prevent exactly that*, and the evidence line that hid its own evidence first by ordering and then by truncation. This is the sharper form of the entry above: not "the generation that fixes X repeats X" but **look one step to the side of what you just changed, before anything else**. Narrowing a value silently falsifies the sentences written about the old one, so re-grep the marker you planted rather than trusting that it will speak up. What made four rounds affordable was a battery of canned fixtures at $0 against a $0.25 live probe — re-verifying every branch after each repair cost one live run. And the trap is not confined to the code: the reviewer's own first negative silently failed to substitute and briefly read as "the ordering does not matter", the same failure the fixture generator's `assert n == 1` exists to prevent. A checker gets no exemption from the discipline it is checking for.
- **An invisible character is not caught by reading**: the call graph emptied because two of four places built an edge key with a NUL separator and two with a space. Terminals render NUL as a space, so every read of those four lines agreed with itself, and an independent reviewer misdiagnosed the cause on the first pass for the same reason. What exposed it was not analysis but one line of arithmetic — *my model predicts 1 edge, the measurement says 0* — which the reviewer nearly skipped as too obvious. **When behaviour and code disagree, measure the bytes**, and run the cheap check before the clever one.
- **A negative test that passes has not vindicated the fix — it has failed to cover it**: gen-089 removed a repair and no test went red, which reads as "this was unnecessary". Three attempts later the case that made it load-bearing appeared (a *new* competing definition, where the stale edge's endpoints are both untouched files) and the negative went red. Reading the green as permission would have reverted a correct fix.
- **Deferred means an open risk, and installing must not damage what the user already runs**: gen-079 wrote "adapter is two, so the gap is two" and covered one; a day later the uncovered half took the user's *other* tool offline — REAP wrote an agent file its client could not parse, and one bad file invalidates a whole config. Say what breaks if a deferral is wrong, and verify the client accepts what you wrote, not merely that the file landed.
- **An inherited deferral is a claim to re-measure, and the grounds you give must be covered by what you build**: gen-084 declined a fix because the branch looked unreachable; gen-085 disproved that in one `git log` — the version had been lower until that morning, and checkouts are not published. Then it fixed the two paths the user names and left the *checkout* path, the very one its argument had rested on, while a test asserted the old advice was correct there. A gap is found by the next reader; an assertion persuades them.
- **A check can carry the defect it checks for, and your negative tests only cover the failures you imagined**: the new gate asked whether a version existed and never whether the package did — npm's `E404` went to stderr, which the gate discarded, so a typo in the name passed as "could not check". Every failure mode that had occurred to its author was tested and red. Ask separately which inputs make a check fail *open*, and make that the exception you have to justify. And an assertion that cannot separate the two states is the same failure one level down: gen-086 proved an error message honoured the user's setting by looking for `REAP_DAEMON_BIN` in it — which the generic advice it was supposed to have replaced also spells. Name something present in only one of the states, and let the negative run tell you (one failure where two were due).
