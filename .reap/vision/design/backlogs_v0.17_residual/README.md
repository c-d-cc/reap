# v0.17 잔여 backlog — 보관본

> **전제: 이 중 상당수는 삭제된다.** 재검토는 "무엇을 할까"가 아니라
> **"이 중 무엇이 아직도 실제로 일어나는가"** 를 묻는 자리다.

## 왜 이 폴더가 있는가

v0.17 은 26세대(gen-071~096) 중 **22세대를 배포·게이트·자기 정합성에 썼다.** 실측:

| 무엇을 했나 | 세대 |
|---|---|
| 배포·설치 결함 (npm 경로, auto-update, uninstall, adapter, XDG, install script 차단) | 9 |
| 게이트·CI·테스트 인프라 | 7 |
| 자기 정합성 (문서와 규칙이 서로 안 맞음) | 5 |
| daemon 폐기·청소 | 3 |
| 문서 사이트 | 1 |
| **새 사용자 기능** | **0** |

이 9건은 그 시기의 부산물이다(**gen-099 가 1건을 해소해 지금 8건**). **REAP 자기 기계장치에 대한 것**이고, 사용자 가치를 가진 것은
indexer 관련 2건뿐이다. 게이트가 backlog 를 만들고, 그 backlog 를 처리하는 세대가 다시 게이트를
만드는 순환에 있었다.

v0.18 은 그 순환의 원인 — **npm CLI 가 남의 홈 디렉토리에 파일을 쓰는 배포 형태** — 를 plugin 전환으로
제거한다. 그러면 위 9세대 중 8세대가 다룬 결함 class 가 애초에 존재하지 않는다.

**따라서 지금 이것들을 고치면 상당수가 헛일이다.** `life/backlog/` 에서 꺼내 여기 둔 이유가 그것이다.

## 언제 다시 여는가

**plugin 전환이 안정화된 뒤.** 그전에는 어느 것이 살아남는지 판정할 수 없다.

부수 효과 하나: `scanBacklog` 은 `.reap/life/backlog/` 만 읽으므로, 여기 있는 동안 이것들은
`reap run start` 의 backlog gate 에 뜨지 않는다. **의도된 것이다** — v0.17 의 잔여물이 v0.18 계획에
섞이지 않는다.

## 재검토할 때 볼 것

각 항목의 본문은 그대로다. 아래는 **본문에 없는 것** — 그때 물어야 할 질문과, 지금 시점의 운명 추정.

### 소멸 후보

**`checkautoupdateguard-는-호출되는-곳이-없다-...`**
`autoUpdateMinVersion` 하한이 `performAutoUpdate` 5단계에서만 강제되어, 이미 최신인 사용자는
하한 경고를 영원히 못 본다는 것.
→ **물을 것: plugin 전환 후에도 REAP 이 자기 버전을 스스로 갱신하는가.** 클라이언트가 plugin 을
갱신한다면 auto-update 경로 자체가 재설계 대상이고, 이 함수는 배선이 아니라 삭제가 답이 된다.

**`reap-uninstall-이-판정-불가를-판정으로-말한다-...`**
`detectInstallKind` 가 `unknown` 일 때 "this copy is a unknown install" 이라고 **종류를 단정**한다.
동작은 옳고 문장만 틀렸다.
→ **물을 것: plugin 전환 후 `reap uninstall` 이 무엇을 지우는가.** 사용자 레벨 자산을 CLI 가
뿌리지 않게 되면 이 명령의 대부분이 사라지고, `detectInstallKind` 도 함께 간다.

**`자기진단-게이트의-path-주석이-...`**
gen-092 가 PATH 주석이 설명하던 원인을 없앴다. 본문은 두 갈래(주석만 갱신 / PATH 줄 제거로
살아있는 회귀 검사화)를 제시한다.
→ **물을 것: 자기진단 게이트 §2·§8 이 plugin 전환 후에도 같은 형태인가.** tarball 설치·전역 제거를
검사하는 절이라 형태가 바뀔 가능성이 높다. 바뀐다면 이 판단은 그 재설계 안에서 한다.

### 살아남음 — 사용자 가치

**`community-detection-재설계-...`** / **`process-tracing-재설계-...`**
gen-089 이 daemon 폐기 시 **의도적으로 이식하지 않은** 분석 둘. 전자는 Louvain 이 아니라 연결
컴포넌트여서 cohesion 이 상수 1.00 이었고, 후자는 진입점 판정이 call resolution 품질에 종속돼
상한 75 에 도달했다.
→ **물을 것: call resolver 가 아직도 이름 기반인가.** 두 backlog 모두 그 위에 서 있다. 특히
process tracing 은 call resolution 개선이 **선행 조건**이지 병행 항목이 아니다.
→ 이 둘은 **plugin 전환과 무관하다.** v0.18 범위 밖으로 명시했으므로 v0.19 이후 후보.

### 살아남음 — 자기 기계장치이지만 plugin 과 무관

**`reap-update-mark-migrated-가-버전을-못-읽으면-...`**
`packageVersion()` 이 `0.0.0` 을 돌려주면 `--mark-migrated` 가 프로젝트 기록을 **낮춘다**.
→ **migration layer 는 plugin 전환 후에도 필요하다** (genome 은 사용자 소유라 규칙 전달 채널이
계속 있어야 한다). 그대로 유효하며, 수정 범위도 작다.

### 해소됨

**`list-carrierssh-가-산문-속-...`** — **gen-099 에서 해소, 파일 삭제.** carrier ID 가
`<slug>-<hash8>` 로 바뀌면서 같은 파일을 만지게 되어 함께 처리했다. 해법은 이 backlog 가
제시한 A/B/C 어느 것도 아니다: **꺾쇠를 포함하면 표식이 아니라 언급**이라는 한 줄 규칙이다.
B(인라인 코드 배제)는 실측하면 틀렸다 — 5개 로케일의 표식은 TS 문자열 안이지만 진짜 carrier 다.

**`층2-게이트-판정부에-자동-회귀-검사가-없다-...`**
`check-agent-integration.sh` 의 8개 분기 중 라이브 실행이 지나는 것은 1~2개. gen-091 의 canned
fixture 18종은 커밋되지 않았다.
→ **물을 것: 무엇이 남는가 — 층2 게이트인가, bash 하네스 부재라는 사실인가.** 전자는 plugin 전환으로
형태가 바뀌지만 **후자는 남는다.** `check-self-diagnosis.sh` / `check-version-floors.sh` /
`check-docs-version.sh` 도 같은 상태다. 재검토 시 **하네스 쪽으로 다시 쓰는 것**이 맞을 수 있다.
