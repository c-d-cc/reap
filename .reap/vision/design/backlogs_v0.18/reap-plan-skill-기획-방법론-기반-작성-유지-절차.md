# /reap.plan skill — 기획 방법론 기반 작성·유지 절차

> 사용자 결정 (2026-08-19): `/reap.plan` 은 **작성 + 유지를 겸한다**. 질문 절차는 **`interview` skill 을 호출**하고 자기가 갖지 않는다. 기반은 제공된 **기획 방법론 문서**(`~/cdws/autoknowme6/temp/docs/methodology-ko.md`, 688줄)다.
>
> **선행**: `plan-reap-최상위-기획-정본-자리.md` — 자리가 먼저 있어야 채울 수 있다.

## Problem

`plan-...` backlog 가 `.reap/plan/` 자리를 만들지만, **채우고 유지하는 절차는 만들지 않는다** (그 backlog 의 S6 에서 명시적으로 분리).

자리만 있으면 두 가지가 일어난다:

- **비어 있는 채로 남는다.** 기획을 문서로 옮기는 것은 부담이 큰 일이고, 도와주는 것이 없으면 안 한다
- **채워도 무너진다.** 정본이 둘이 되고, 용어가 흔들리고, 구현된 것과 아닌 것이 뒤섞인다. 방대한 문서일수록 빨리 무너진다

그리고 REAP 은 이 절차를 **처음부터 만들 필요가 없다.** 검증된 방법론 문서가 있고, 그것으로 만들어진 실제 산출물(9문서 1,380줄)도 확인했다. **이식할 것을 고르는 일**이지 발명하는 일이 아니다.

## Solution

`/reap.plan` skill 을 신설한다. 규율의 소유자는 **skill 하나**이며, CLI 는 아무것도 하지 않는다 (코드로 기획 엔진을 만들지 않는다).

### S1. 작성 + 유지를 한 자리에서

두 일이 한 skill 인 근거: **둘 다 "하나의 진실 원천을 지킨다"는 같은 규율을 쓴다.** 새로 쓸 때도 고칠 때도 판단해야 하는 것은 같다 — 이 사실의 정본이 어디인가, 여기 쓰면 두 번째 원본이 생기는가.

조회는 제외한다. 파일을 그냥 읽으면 되므로 skill 이 필요 없다.

### S2. 방법론에서 이식할 것

방법론 문서 688줄을 통째로 옮기지 않는다. **skill 이 담을 만큼만** 가져온다.

**핵심 원칙 — 이식**

| 원칙 | 내용 | 왜 |
|---|---|---|
| **보이는 문제 100개 중 10개만 말한다** (§1.8) | 에이전트와 인간은 **인지 예산이 다르다**. 쟁점 80개를 열거할 수 있어도 인간은 처리하지 못한다. 3계층으로 처리 — **A: 지금 묻는다(최대 3개) / B: 가정으로 결정하고 문서에 한 줄 통보 / C: 문서에 쓰지도 않는다** | 방법론이 **★에이전트 필수**로 표시한 유일한 항목. interview backlog 의 인지부하 원칙과 같은 결론에 독립적으로 도달해 있다 |
| 선별 기준 (§1.8) | **되돌리기 비용 · 파생성 · 정보 독점** 셋 중 하나면 지금 꺼낸다 | "무엇을 3개로 고를 것인가"의 판단 기준. 이것 없이는 A 계층이 자의적이 된다 |
| 상위 결정 우선 (§1.8) | 세부 쟁점 대부분은 **상위 결정의 종속 변수**다. 상위 전에 하위를 묻는 것은 답을 두 번 받는 짓 | 질문 수를 줄이는 실질적 수단 |
| 고객의 말은 요구사항이 아니라 증상 (§1.1) | 발언을 그대로 목록화하지 않는다 | 안티패턴 1번의 근원 |
| 백지 앞에서 사람은 말하지 못한다 (§1.2) | **틀린 초안을 먼저 제시**하고 차이를 수집한다 (가설·직면 루프) | 질문만으로는 안 나온다. interview 의 "선택지 제시"와 같은 뿌리 |
| 추상 대신 최근 3건 (§1.3) | "보통 어떻게 하세요" 대신 "최근 3건을 순서대로" | 이상화된 답 차단 |
| 범위는 **제외 목록**으로 확정된다 (§1.4) | Out of Scope 를 명문화하지 않으면 범위가 없다 | REAP 의 milestone·interview backlog 가 이미 같은 결론 |
| 하나의 진실 원천 (§1.7) | 같은 사실을 두 곳에 쓰면 한쪽이 바뀌는 순간 다른 쪽은 거짓말이 된다 | **유지 기능의 판단 기준 전체가 여기서 나온다** |
| 완결성보다 진행 (§1.9) | 90% 문서로 착수하는 것이 100%를 기다리는 것보다 낫다. **단 되돌리기 비용이 큰 항목은 예외** | 무한 인터뷰 차단 |

**프로세스 — 주제만 이식**

P0~P5 (맥락 스캔 → 문제 정의 → 범위 확정 → 구조 설계 → 명세화 → 검증·합의)의 **주제와 종료 조건**만 가져온다. 각 단계의 질문 은행 전문은 옮기지 않는다 — 질문은 interview 가 만든다 (S3).

**그린필드 / 브라운필드 분기** (§3) — 전략이 갈린다. 그린필드는 인위적으로 기준점을 만들고, 브라운필드는 **말보다 자료를 먼저 읽는다**. REAP 의 `reap init` 이 이미 greenfield/adoption 을 자동 감지하므로 **접점이 있다** — skill 이 그 판정을 재사용할 수 있는지 확인할 것.

**안티패턴 (§6)** — 표 전체는 크지만 **기획 문서에서 실제로 반복되는 것 몇 개**는 이식 가치가 있다: 화면부터 그림 / "일단 다 넣죠" / 예외 미정의 / 용어 혼용 / 이미 답한 것을 재질문.

**이식하지 않을 것**

| 방법론 요소 | 왜 |
|---|---|
| **결정 로그(§4.3)** | **plan backlog 에서 배제 결정.** REAP 은 lineage + completion artifact 로 이미 기록한다. 참고 사례에서 잘못된 anchor 로 작용한 전례도 있다 |
| 마일스톤 (§4.7) | milestone backlog 소관 |
| 세션 handoff (§4.2, §4.5) | `memory/shortterm.md` |
| 이슈·실행계획 (§4.6) | backlog + planning artifact |
| 동시 세션 조율 SQLite (§4.1-1) | REAP 범위 밖 |
| ID 체계 (§7) | plan backlog 가 **구조를 규정하지 않기로** 했다. ID 를 요구하면 형식을 강제하는 셈 |
| 저장소 폴더 구조 (§4.1) | 같은 이유 |
| 질문 은행·기술 카탈로그 (§5) 의 **전문** | interview 소관 (S3). 다만 **질문 예산 "한 턴에 3개 이하"** 는 §1.8 과 함께 이식 |

### S3. 질문 절차는 interview 에 위임

`/reap.plan` 은 **"무엇을 물을 것인가"(기획 단계별 주제)만 지정**하고, **"어떻게 물을 것인가"(형식·진행 규율)는 `interview` skill 이 소유**한다.

근거: interview backlog 가 이미 **"규율을 여러 곳에 복붙하면 carrier 문제가 된다"** 고 적었다 (issue #21 과 같은 종류). 질문 형식·진행 규율을 여기 다시 쓰면 그 문제가 그대로 재발한다.

**따라서 이 backlog 는 interview skill 에 의존한다.** interview 가 없는 상태에서 만들면 자체 절차를 갖게 되고, 그 순간 규율이 두 곳에 생긴다.

**확인 필요** — §1.8 의 3계층(A 묻는다 / B 가정 / C 넘긴다)과 선별 기준은 **어느 쪽 소유인가**:
- interview 의 일반 규율로 올리면 모든 interview 가 혜택을 본다
- plan 전용으로 두면 interview 는 단순해진다

**interview 쪽으로 올리는 것이 유력**하다 — 그 원칙은 기획에만 해당하지 않는다. 그렇다면 **interview backlog 를 갱신해야 하므로 순서가 얽힌다** (Related 참조).

### S4. 유지 기능

- **상태 갱신** — 구현된 항목의 상태를 바꾼다. plan backlog 의 S3(상태 표시 단위)가 정해져야 가능
- **정합성 점검** — 문서 간 모순, 정본이 둘이 된 곳, 어디서도 가리키지 않는 고아 문서. 판단 기준은 §1.7
- **진입점 갱신** — plan backlog 의 S5 가 "누가 갱신하는가"를 미결로 두었다. **여기가 유력한 답**이다 — 채택하면 그 미결이 함께 닫힌다
- **용어 일관성** — 안티패턴 "용어 혼용"에 대응

### S5. 형식을 강제하지 않는 것과의 긴장

plan backlog 의 S2 는 "구조를 규정하지 않는다"인데, **skill 이 문서를 써 주면 그 출력 형식이 사실상 표준이 된다.** 강제는 아니지만 기본값이 생기고, 기본값은 대부분 그대로 남는다.

완화안:
- **기존 문서가 있으면 먼저 읽고 그 형식을 따른다** — 백지일 때만 skill 의 기본값을 쓴다
- 기본값을 **최소한**으로 둔다 — 문서 하나의 뼈대 정도이지 폴더 구조까지는 아니다

결정 필요 (Open Decisions).

## Verification

1. **`/reap.plan` 이 양 클라이언트에서 실제로 노출되는가** — 파일이 놓인 것과 클라이언트가 읽는 것은 별개다 (gen-063/079). claude-code 는 층2 검사, opencode 는 현재 slash command 검증 수단이 없음을 기록
2. **skill 이 interview 를 실제로 호출하는가** — 자체 질문 절차를 만들어버리면 S3 의 위임 설계가 무력해진다. **skill 본문에 질문 형식·진행 규율이 복제되어 있지 않은지** 확인
3. **§1.8 이 실제로 지켜지는가** — 백지 기획으로 돌려보고 **한 턴 질문이 3개를 넘지 않는지**, B 계층(가정)이 문서에 한 줄로 통보되는지 확인. 이것이 안 지켜지면 방법론 이식이 이름만 남은 것이다
4. **결정 로그를 만들지 않는가** — skill 이 `decisions/` 를 자동 생성하거나 결정 기록을 plan 에 쓰지 않는지 확인 (plan backlog 의 배제 결정)
5. **기존 형식을 따르는가** (S5) — 이미 문서가 있는 plan 에 skill 을 돌렸을 때 형식이 갈아엎어지지 않는가
6. **유지 기능이 실제로 잡는가** — 정본이 둘인 상태를 **일부러 만들어 놓고** 돌려서 잡히는지 확인. 통과부터 보면 그 검사가 무력한지 알 수 없다 (gen-073 교훈)
7. **skill 없이도 plan 이 성립하는가** — plan backlog 의 검증 항목과 겹친다. skill 이 plan 의 전제가 되어선 안 된다
