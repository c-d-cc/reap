## 왜 닫았나

착수 근거가 *"REAP 이 외부 프로젝트로 확산되면 사용자의 코드베이스는 본 repo 보다 크다"* 였다. **아직 확산되지 않았다.** `vision/goals.md` 의 "외부 프로젝트에서 core lifecycle 검증" 은 미완이고 실사용자는 사실상 저자 한 명이다.

*(작성 당시 인덱서는 opt-in 이었다. 지금은 CLI 와 함께 무조건 배포되므로 **모든 사용자가 쓴다** —
확산이 일어나면 규모 압력이 더 빨리 온다는 뜻이고, 그것이 재검토 조건을 앞당길 수 있다.)*

반면 설계 난이도는 크다 — 노드 ID 통합(`file::name` vs SCIP symbol ID)을 조사 문서 스스로 **핵심 난제**로 불렀고, 그 외에 감지·혼합 그래프·트리거 모델·폴백 경계가 남는다.

**존재하지 않는 규모를 위한 설계**이므로 보류한다. 이것은 2026-08-19 에 파생 backlog 11건을 정리하며 세운 기준과 같다 — *"지금 존재하는 사용자에게 실제로 일어나는가."*

## 구조적 한계 4가지 (2026-08-19 코드 확인, 2026-08-22 재확인)

**소규모~중규모 단일 repo 에서는 잘 동작한다** — 본 repo 가 dog-fooding 중이며 문제 없다.
아래는 그 범위를 벗어날 때의 이야기다. 표의 `indexer/*.ts` 는 `src/indexer/*.ts` 를 가리킨다.

| # | 한계 | 위치 | 성격 |
|---|---|---|---|
| 1 | **Call resolution 이 이름 기반 휴리스틱** — 타입 해석 없이 동명이인을 이름+위치로 고른다. 오버로드·동일 메서드명·인터페이스 구현체 다수에서 오답 edge, 동적 디스패치/고차 함수는 미탐. **정확도가 규모에 반비례** | `indexer/call-resolver.ts:11-33` | Tree-sitter 가 구문만 보고 의미를 못 보는 데서 오는 본질적 차이 |
| 2 | **그래프 전체가 인메모리** — SQLite 는 write-through 영속화용이고 쿼리는 메모리 그래프에서 처리. 메모리가 코드베이스 크기에 선형 비례하며 **상한이 없다** | `indexer/graph.ts:3-8` | 수백만 LOC 급의 첫 번째 벽 |

**한계 4 는 더 이상 성립하지 않는다** (`[실행]` 2026-08-22 확인). `src/indexer/pipeline.ts` 가
incremental 경로에서 **두 edge 종류를 전량 삭제한 뒤 전체 그래프에 대해 다시 해석한다** —
`graph.removeEdgesOfKind("IMPORTS")` (`:88`) 와 `graph.removeEdgesOfKind("CALLS")` (`:195`).
스냅샷이 `refs` 와 `specifiers` 를 저장하므로 재파싱하지 않은 파일의 참조까지 재해석 대상이 된다.
`tests/e2e/index-incremental.test.ts` 의 판정 기준이 **"incremental 결과 == full rebuild 결과"** 이며
edge 집합 자체를 비교한다.

*이 항목을 지우지 않고 취소선으로 남긴다* — 재검토하는 사람이 "4개 한계"라는 표현을 다른 곳에서
보고 찾을 때 어디로 갔는지 알아야 하고, **해소됐다는 사실 자체가 SCIP 의 이득을 줄인다.**

## SCIP 이 푸는 것과 못 푸는 것

**SCIP** (https://scip-code.org/) — Sourcegraph 가 LSIF 후속으로 만든 protobuf 기반 언어 중립 인덱스 포맷. 인덱싱 단계와 프론트엔드를 분리하는 것이 핵심 설계.

**푸는 것: 한계 1 하나뿐이다.** 연결이 문자열 매칭이 아니라 전역 고유 심볼 ID 매칭이 되어 동명이인 문제가 원리적으로 사라진다. **한계 2·3·4 는 그대로 남는다** — 인메모리 그래프도, 단일 repo 가정도, 부분 갱신 정합성도 SCIP 이 해결해 주지 않는다.

**못 푸는 것: 사용자 환경 요구사항.**

| 인덱서 | 요구사항 |
|---|---|
| scip-typescript | `tsconfig.json` + **`npm install`/`yarn install` 이 끝난 상태**, Node 18/20 |
| scip-java | gradle / maven / sbt / bazel 중 하나로 **빌드 가능한 상태**. *"빌드 시스템 지원 없이는 거의 무용"* |
| scip-python | 동작하는 python 환경 |

이건 **사용자의 저장소에서 일어나는 일**이다. 인덱서를 어디에 두든, 어떤 방식으로 부르든 `gradle build` 가 필요 없어지지 않는다 — **패키징으로 없앨 수 있는 비용이 아니다.**

추가 제약 둘:
- 인덱서마다 **런타임이 다르다** (scip-java 는 JVM, scip-go 는 Go). 15개 언어분 번들은 비현실적이라 "사용자 환경에 있으면 쓴다" 모델이 될 수밖에 없다
- **인덱싱 비용이 빌드에 준한다.** 지금은 질의가 스스로 갱신하고 eager 트리거가 커밋 시점 하나뿐이라 비용이 작지만, SCIP 은 그 모델을 그대로 쓸 수 없다

## 채택하기로 했던 형태 (유저 결정 2026-07-26, 보류됨)

**Tree-sitter baseline + SCIP 승격 하이브리드.** SCIP 으로 Tree-sitter 를 대체하지 않는다 — 대체하면 "설치 즉시 동작"이라는 REAP 의 성질을 잃는다.

- Tree-sitter: 항상 동작, 설치·빌드 요구 없음
- SCIP: 사용자 환경에 인덱서/툴체인이 있을 때만 활성화 → call resolution 이 이름 휴리스틱에서 의미 기반으로 승격
- 없으면 조용히 Tree-sitter 폴백 — 인덱서가 grammar 로드 실패에 이미 쓰는 패턴이다 (실패를 기록하고 `reap index status` 가 경고로 노출)

**MCP wrapper 는 추가하지 않는다** (유저 결정 2026-06-28). 본 건은 MCP 가 있어야 풀리는 문제가 아니다.
*(당시 근거는 "HTTP API 가 이미 있다"였다. 그 API 는 없어졌고 지금은 `reap index` CLI 가 그 자리다 —
결정은 유지되지만 근거는 바뀌었다.)*
