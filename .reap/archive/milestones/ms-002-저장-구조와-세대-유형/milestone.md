**끝나면 할 수 있는 것:** `.reap/`가 vision · life · archive 3단으로 서고, 세대가 유형과 무관하게 하나의 계열(`gen-NNNN-type`)로 쌓인다. milestone에 속하지 않는 fix 세대를 열고 닫을 수 있고, 닫은 것을 `cleanup`이 archive로 내린다. **`.reap/map.md`를 열면 각 계층이 무엇인지 알 수 있다.** **이 리포 자신이 그 구조로 옮겨져 있다.**

**일부러 갖지 않는 것:** `build-context` · `decide` · `doctor` · `seq` · backlog/idea 명령 · `carve-milestone` · `author-plan` · `interview`. 바닥만 굳힌다.

**왜 지금인가:** 로드맵의 증분 2("맥락이 쌓인다")를 먼저 하면 곧 갈아엎을 레이아웃 위에 짓게 된다. `gen-0011-plan`에서 저장 구조와 id 계열이 통째로 바뀌었으므로 그 위에 얹기 전에 바닥을 굳힌다.

### 작업 갈래

상세는 `tasks/`에 있다.

| task | 무엇 | 상태 |
|---|---|---|
| 2.1 | 저장 레이아웃 재편 — vision · life · archive | 완료 (gen-0012-exec 코드 · gen-0013-exec 리포) |
| 2.2 | id 계열 통합 — `gen-NNNN-type`, 레지스트리 하나 | 완료 (gen-0015-exec) |
| 2.3 | fix 유형 · `cleanup` skill · `mark --archived` | 완료 (gen-0016-exec) |
| 2.4 | `map.md` · skill · 훅 최종 갱신과 전체 검증 | 완료 (gen-0017-exec) |
| 2.5 | `cleanup`의 기준을 참고 가치로 바꾼다 | 완료 (gen-0020-exec) |

**각 task가 코드와 이 리포를 함께 옮긴다.** 처음 계획은 마이그레이션을 2.4에 몰아두는 것이었는데 **그것이 틀렸다** — `gen-0012-exec`이 코드를 옮기자마자 이 리포에서 `ctx`·`make`·`mark`가 전부 죽었다. REAP가 자기 자신으로 만들어지는 한, 저장 구조를 바꾸는 작업은 도구와 그 도구의 유일한 사용자를 같이 옮겨야 한다. 근거는 `gen-0012-exec`의 Dead Ends에 있다.

**2.1 → 2.2 순서는 그대로다.** 경로가 먼저 서야 id가 어디에 놓일지 정해진다.

**2.5는 계획에 없던 것이고, 한 번 잘못 정의됐다가 다시 잡혔다.** 2.3이 만든 `cleanup`이 milestone 소속을 기준으로 삼는 바람에 plan·fix 세대가 archive로 갈 길이 없다는 것이 드러났다. `gen-0018-plan`이 "닫히는 즉시 archive"로 고치려 했으나 그것은 `life/generations/`의 목적을 깨는 것이었고, `gen-0019-plan`이 되돌린 뒤 **기준을 참고 가치로** 다시 세웠다.

### 완료 판정

`bun test` 통과 · `bun run typecheck` 오류 0 · `./tests/hook.test.sh` 통과, 그리고 **손수 두 바퀴**:

*빈 프로젝트:* `init` → `make milestone` → `make generation`(exec·plan·fix 셋 다) → 커밋 → `mark --closed` → `mark milestone --closed` → `mark generation --archived` → `ctx`가 전부 정상.

*이 리포:* 마이그레이션 후 `reap ctx`가 옛 경로를 하나도 가리키지 않고, 새 세션에서 맥락이 정상 주입된다.

### 증분 2가 끝나면 물어볼 것

1. **vision / life / archive 3단이 실제로 도움이 되던가?** 무엇을 찾을 때 어디를 봐야 할지 덜 헷갈렸는가, 아니면 한 겹이 더 생겼을 뿐인가.
2. **`gen-NNNN-type` id가 읽기 좋던가?** 인용할 때 길지 않았는가. 정렬이 시간순인 것이 실제로 쓸모 있었는가.
3. **fix 유형을 실제로 골랐는가?** 골랐다면 경계("되돌리는 일만")가 헷갈린 적은 없었는가. 새 기능을 fix로 지으려는 유혹이 있었는가.
4. **`cleanup`을 부르게 되던가?** 아니면 archive가 비어 있는 채로 남았는가. skill에 맡긴 것이 지켜지는가.
5. **마이그레이션에서 잃은 것이 있는가?** 재번호 때문에 옛 커밋 메시지를 못 따라간 적이 있었는가.

### Fitness

사람이 닫으며 여섯에 답했다. **넷은 "이대로", 둘은 바꾼다.**

**1. vision / life / archive 3단** — **도움됐다.** 어디를 볼지 덜 헷갈렸다. 유지한다.

**2. `gen-NNNN-type` id** — **좋다. 정렬이 시간순인 것이 실제로 쓸모 있었다.** 재번호의 대가(옛 커밋 메시지가 사라진 id를 가리키는 것)는 매핑으로 갚아졌고 불편으로 보고되지 않았다.

**3. subagent에 맡긴 것** — **느렸다. 직접 하는 게 빨랐을 것이다.**

task 다섯 중 넷을 subagent가 했다. 품질 문제는 아니었다 — 개별 리뷰가 다섯 번 통과했고 최종 리뷰의 Critical은 0이었다. 문제는 **왕복이다.** dispatch → 리뷰 → 수정 라운드 → 재리뷰가 task마다 돌았고, 그중 절반은 문서 몇 줄을 고치는 일이었다.

**ms-003은 사람이 직접 한다.**

**4. milestone 크기** — **맞다. 이 정도로 유지한다.** task 5 · 세대 9(exec 6 + plan 3) · 커밋 40여 개. 계획이 세 번 바뀐 것은 크기 문제가 아니라 설계가 겪으면서 드러난 것이다.

**5. fix 유형** — **두고 본다.** 이번 milestone에서 **한 번도 고르지 않았다** — 되돌릴 것이 없었기 때문이지 설계가 틀려서가 아니다. ms-003에서 실제로 쓰이는지가 판정 재료다.

**6. `cleanup`** — 이 종료가 **첫 실행**이다. 결과는 아래 `handoff.md`에 남는다.

### 이 milestone이 남긴 것 — 다음 증분이 판단할 재료

**계획이 세 번 바뀌었다.** 마이그레이션 시점(2.1 도중), `map.md` 추가(2.4 재정의), archive 기준(2.5 신설 후 재정의). 셋 다 **만들어보고 나서야 드러난 것**이고, 셋 다 사람이 잡았다.

**설계가 두 번 뒤집혔고 두 번 다 사람이 잡았다.** `cleanup`의 기준과 `life/generations/`의 목적. 후자는 **그 목적이 spec 어디에도 안 적혀 있었기 때문**이고, 그 교훈이 `lessons.md`로 졸업했다("구조를 적을 때 그 구조의 목적도 적는다").

**이것이 다음 증분의 가장 중요한 입력이다** — agent가 혼자 도는 동안 놓친 것이 전부 "적히지 않은 의도"였다.
