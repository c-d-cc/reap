## Lessons Learned

### 잘 된 것 — 게이트가 만들어지자마자 실제 결함을 잡았다

의도적으로 깨뜨리기 **전에** 이미 fail 했다. `invariants.md` 가 placeholder 로 오판되고 있었다 — 검사가 `-` 로 시작하는 줄을 전부 제외하는데 그 파일은 본질적으로 불릿 목록이라 산문이 없다.

**REAP 이 배포하는 파일이 REAP 검사를 통과 못 하는 상태**였고, 이는 gen-075 의 genome threshold(100 < 배포 193줄)와 정확히 같은 유형이다. 두 번 다 "자기 도구로 자기를 재보지 않아서" 생겼고, 이번엔 그 재보는 행위 자체를 게이트로 만든 것이 즉시 성과를 냈다.

### 잘 된 것 — negative test 가 내 오해를 드러냈다

게이트가 #22 를 잡는지 확인하려고 `isCanonical` 을 false 로 바꿨는데 **exit 0** 이 나왔다. gen-076 이 해당 검사 자체를 제거했으므로 그 방법으로는 재현되지 않는다는 걸 몰랐다.

정확히 재현하니 19건 검출 + exit 1. **통과만 봤다면 게이트가 무력한 줄 몰랐을 뿐 아니라, 내가 직전 세대에 짠 코드를 잘못 기억하고 있다는 것도 몰랐을 것이다.**

gen-073 의 "먼저 실패시켜라"는 검사의 유효성 확인이 목적이었는데, 실제로는 **작성자의 이해까지 검증한다**.

### 잘 된 것 — 허용 목록 대신 시나리오를 고쳤다

`application.md` 미작성 경고가 뜨자 두 선택지가 있었다: allowlist 에 넣거나, 시나리오가 그 부분을 채우게 하거나.

allowlist 는 늘어나면서 게이트를 무력화한다 — gen-075 가 "경고가 상시 뜨면 신호 가치 0"을 확인했고, 그게 바로 #22 가 6세대 방치된 이유다. **게이트를 만들면서 그 게이트를 무디게 하는 장치를 함께 넣을 뻔했다.**

자기진단은 "설치가 건강한가"를 보는 것이지 "프로젝트가 완성됐는가"가 아니다. 대화로 채워지는 부분은 스크립트가 채우고 진단하는 것이 정확하다.

### 개선점 — backlog 가 몰랐던 제약이 범위를 바꿨다

backlog 는 "자기진단을 CI 에 넣자"고 했고 유저도 승인했으나, **`tests/` 가 private submodule 이라 CI 에서 테스트를 못 돌린다**는 사실은 learning 단계에서야 드러났다.

자기진단 자체는 tests/ 가 필요 없어 그대로 넣었지만, "테스트도 CI 에"는 PAT 발급이 필요해 분리했다. **agent 가 대신할 수 없는 사용자 작업**이 끼면 범위를 나누는 것이 맞다.

gen-073 이래 "backlog 의 주장도 검증 대상"이 반복 확인되고 있다 — 이번엔 주장이 틀린 게 아니라 **전제가 불완전**했다.

### 개선점 — carrier 표식의 효과는 아직 미검증

2 carrier·19 files 에 표식을 심고 고아 탐지가 동작함을 확인했다. 그러나 **이것이 실제로 다음 사고를 막는지는 알 수 없다** — 표식은 "값을 바꾸는 사람이 옆에 있는 주석을 본다"는 가정에 기대고 있다.

가정이 틀리면(주석을 무시하고 값만 고치면) 열거와 다를 바 없어진다. 몇 세대 관찰이 필요하며, 노이즈로 인식되기 시작하면 접근을 재검토해야 한다.
