## Lessons Learned

### 글롭으로 묶은 제외는 항목마다 근거를 적을 수 없다

제외 표에 이렇게 적었다:

> `src/templates/migration/v0.17.{5,6}.md` — 산문이 아니라 실행 지시. 지우면 `daemon: true` 를 가진 프로젝트가 설정을 안고 남는다

**그 근거는 v0.17.6 에만 참이었다.** v0.17.5 는 정반대(설치 지시)를 담고 있었다. **두 파일을 하나로 검증했고, 검증한 쪽이 무고한 쪽이었다.**

교훈은 "더 꼼꼼히 보자"가 아니다 — 그것은 이미 실패한 방법이다. 다음에 쓰일 형태로 적으면:

> **묶으면 검증 횟수가 항목 수보다 적어진다.**

한 행은 근거를 하나만 담고, 근거 하나를 세우는 동안 확인하는 항목도 하나다. 그러니 N개를 한 행에 묶은 순간 **N−1개는 읽히지 않고 통과한다** — 어느 것이 안 읽혔는지는 우연이 정하고, 이번에는 하필 유죄인 쪽이었다. 중괄호·와일드카드·"등"·"계열" 이 전부 같은 일을 한다.

처방: 제외는 **경로 하나에 근거 하나**씩 적는다. 그리고 이미 묶여 있는 항목을 보면 그것을 "간결하게 쓴 것"이 아니라 **"여기서 검증이 항목 수보다 적었다"** 로 읽는다.

**같은 세대 안에서 이 교훈이 두 번 값을 했다.** 3라운드에서 `package-lock.json` 을 재생성한 뒤 `npm install` 한 번으로 끝났다고 보고할 뻔했다 — npm 이 `"daemon"` 항목을 `"extraneous": true` 로 **이월했고**, 5개 기준을 하나씩 확인했기 때문에만 그것이 드러났다. "재생성했고 `npm ci` 가 깨끗하다"로 뭉뚱그렸다면 기준 3이 거짓인 채 통과했을 것이다.

**`v0.17.5.md` 와 정확히 같은 형태다** — 확인해야 할 것이 여럿인데 확인 행위를 하나로 묶었고, 묶인 것 중 하나가 유죄였다. 한 번은 제외 표의 중괄호였고 한 번은 "재생성했다"라는 한 문장이었다. **형태는 표기가 아니라 세는 방식에 있다.**

### `grep` 은 제외 집합이 옳다는 전제 위에서만 완결성을 말한다

완결성 주장을 `grep` 0건에 세웠고, 네 번 돌려 네 번 exit 1 이었다. 그동안 **제외한 파일이 `npm i -g <deprecated>` 를 매 세션 컨텍스트에 넣고 있었다.**

grep 은 "이 집합에 문자열이 없다"를 답한다. **집합이 옳은지는 말하지 않는다.** 깨끗한 실행마다 그 전제가 검증되지 않은 채 깔린다.

주장이 *도달 범위*에 관한 것이면 **도달 범위를 재야 한다** — 격리된 신규 프로젝트, 실제 진입점(`reap load-context`), 그리고 같은 바이너리에서의 before/after diff. 이것을 C8 로 신설했다.

### 재현을 믿기 전에 재현 환경을 확인한다

수정 후 첫 측정이 여전히 19였다. 원인은 코드가 아니라 **probe 가 PATH 의 전역 설치를 재고 있었고 내 수정은 저장소 `dist/` 에 있었다.** `node "$PWD/dist/cli/index.js"` 로 바꿔 19 → 13 을 확인했고, `git stash` 로 절을 되살려 같은 바이너리에서 19를 재현해 **probe 가 두 상태를 구분함**을 보였다.

한쪽만 재면 "13이 낮다"는 것만 알 뿐 무엇 때문인지 모른다.

### 없애려던 형태를 세 번 재생산했다

이 세대는 **"검사가 있으나 무력한 상태"** 를 없애러 왔다 — guide 의 회고 완화가 실행 가능한 명령 하나(`npm uninstall -g @c-d-cc/reap-daemon`)를 통과시키고 있었고, 그 완화를 주석이 길게 정당화하고 있었다.

그런데 스스로 같은 형태를 세 번 만들었다:

1. `not.toContain("retired daemon")` — 코드에서 그 문구를 없애면서 assertion 을 그대로 뒀다 (구현 중 스스로 발견)
2. `vite build` 통과를 dangling reference 부재의 근거로 삼았다 — 그 빌드는 타입을 보지 않는다 (evaluator)
3. `grep` 0건을 완결성의 근거로 삼았다 — 제외 집합이 틀리면 조용히 통과한다 (evaluator)

셋 다 같은 구조다: **통과가 무엇을 관측했는지 묻지 않았다.** longterm 의 *"being mid-repair confers no immunity"* 가 다시 확인됐다.

### 산문은 값을 공유할 수 없으므로 값을 갖지 않는 것이 답이다

`REAP_HOME_ENTRIES` 는 3개인데 daemon 을 빼면서 README 는 2개만 열거하게 됐고, 바로 다음 문장이 "나머지는 그대로 둔다"고 말한다 — **daemon 을 한 번이라도 켰던 사람에게 그 약속은 거짓**이다.

고친 방향은 "세 번째를 다시 적기"가 아니라 **열거를 없애기**다. genome 의 *"표식보다 공유가 낫다"* 를 산문에 적용하면, 산문은 값을 import 할 수 없으므로 **애초에 값을 갖지 않는 것**이 유일한 해법이다. `source-map.md` 도 같은 방식으로 고쳤다 — 목록을 적는 대신 소유자(`reap:carrier(reap-home-asset-set)`, `npmRemovalTargets()`)를 가리킨다.

### grep 한 축으로는 로케일 대칭을 판정할 수 없다

`ja.ts` 의 `retiredTitle` 은 `かつてはデーモンがありました` — 가타카나라 `grep -i daemon` 에 잡히지 않는다. **backlog 도 키를 3개로 적었으나 실제로는 4개**(`retiredNote` 누락)였다.

삭제는 grep 이 아니라 **키 이름 기준 + 파일당 정확히 4개 `assert`** 로 했다. 세지 않고 지우면 값이 번역된 곳을 놓친다.

## 3라운드 — 새 backlog 2건을 이번 세대에서 소비

사용자 지시(2026-08-21)로 이 세대가 만든 backlog 2건을 별도로 남기지 않고 소비했다. pending 은 시작 시점과 같은 **15건**으로 돌아왔다.

**`package-lock.json` 재생성.** `workspaces: ["daemon"]` 과 버전 0.17.5 가 남아 있었다. backlog 가 적어둔 판정 기준을 먼저 실패시키고(`npm ci` remove **40**) 재생성 후 **0** 으로 판정했다.

**`npm install` 한 번으로는 통과하지 않았다** — npm 이 `"daemon"` 항목을 `"extraneous": true` 로 남긴다(`daemon/` 디렉토리는 없는데도 옛 lock 에서 이월한다). lock 을 지우고 재생성해야 사라진다. **한 번에 통과했다고 보고했다면 기준 하나가 거짓인 채 넘어갔을 것이다** — 5개 기준을 개별로 확인한 것이 그것을 잡았다.

의존 diff 는 프로그램으로 냈다: before 48 → after 8, **REMOVED 40 / ADDED 0 / VERSION CHANGED none**. 순수 감산이라 baseline 이 안 움직일 것으로 예상했고 실제로 안 움직였지만, **예상이 검증을 대신하지 않으므로** 세 스위트와 `npm pack` 을 거치는 자기진단 게이트를 전부 새로 돌렸다.

**`reap-tree.md` 4건.** `:17`·`:185`·`:274` 는 문구 교체. `:253`(미결 결정 5번)은 **전제만** `reap index` 기준으로 다시 쓰고 **결정은 미결로 남겼다** — 지시는 "backlog 없이 소비"이지 "설계 결정을 지금 내려라"가 아니고, `.reap/.index/` 가 프로젝트별이라는 것은 확정된 사실이라 전제 교체에 새 판단이 필요 없다. 다시 쓰면서 **전제 교체가 새로 만드는 질문**(child 커밋이 움직일 때 parent 인덱스가 언제 낡는가 — 인덱스가 커밋 기준이 되어 생긴 질문)을 명시했다.

**backlog consumed 마킹에 CLI 경로가 없다.** `reap run start --backlog` 이외의 표면이 없고 frontmatter 를 손으로 쓰는 것은 genome 이 금지한다. gen-065 가 그 변형들을 다루려고 만든 `consumeBacklog()` 를 `bun -e` 로 직접 호출했다.

## 4라운드 — 로케일 산문을 사람이 읽었다

사용자 지시로 이 세대의 가장 큰 미검증 축을 닫았다. 네 항목을 각각 확인했다:

| 항목 | 결과 |
|---|---|
| 잘린 절을 가리키는 앞뒤 연결어 | **해당 없음** — 절단면 4곳 × 3로케일 전부 문장 경계에서 잘렸고 다음이 굵은 소제목으로 새로 시작한다 |
| 열거 개수 | **해당 없음** — daemon 은 열거의 원소가 아니라 독립 문단·독립 항목이었다. 개수를 말하는 표현을 전수 대조했고 어긋난 것이 없다 |
| 목차·링크 | **해당 없음** — 지운 README 문단은 `#` 헤딩이 아니라 인라인 굵은 문단이라 앵커가 없다. docs 페이지에는 목차 컴포넌트가 없다 |
| ko/en 의 수정을 같은 자리에 갖고 있는가 | **결함 1건 — 수정함** |

**마지막 항목이 잡아낸 것**: 자리는 맞았지만 **내가 넣은 삽입구가 네 언어에 영어 문장부호를 들여왔다.** 원문은 ko/ja/de/zh 모두 괄호를 쓰고 있었는데 em-dash 삽입구로 바꿨다. ja 는 특히 나빴다 — 연용형(`削除し`) 뒤에 대시가 끼어 문장이 한 번 멈춘다. 네 언어를 각자의 관례(괄호)로 되돌렸고 **en 만 em-dash 를 유지**했다(영어에서는 그것이 관례이고 원문도 그랬다).

**이 결함은 모든 `[실행]` 근거가 초록인 상태에서 남아 있었다** — grep 0건, 문자열 리터럴 5,853개, 배포 번들 13건, exact-match assert, `git diff --stat` 5개 파일 동일. 기계는 **문자열이 거기 있는지**를 보고 **그것이 그 언어로 읽히는지**는 보지 못한다.

`[실행]` / `[negative]` / `[독해]` 표기가 실제로 무언가를 가른다는 증거다. 이 항목을 자동화 가능한 것처럼 적으면 다음 세대가 게이트 초록을 보고 넘어간다 — 그래서 앞으로도 `[독해]` 다.

## 관찰 — 결함이 아니지만 다음에 그 자리를 손대는 사람이 알아야 할 것

**같은 디렉토리를 두 명령이 다르게 부른다.**

```
uninstall.ts:100   "~/.reap/: reap-guide.md, .install-stamp, daemon/ — an allowlist, not the whole directory"
update.ts:289      `removed leftover index data: ${daemonLeftover}`
```

`~/.reap/daemon/` 하나를 두고 앞은 **경로를 지목**하고 뒤는 **이름을 피해 "index data" 라고 부른다.**

**둘 다 틀리지 않았고 의도된 차이다.** `uninstall` 의 목록은 *지금 지워질 것*을 사용자에게 보여주는 자리라 경로를 그대로 대야 무엇이 사라지는지 알 수 있다. `update` 의 한 줄은 *이미 지웠다*는 통보라 daemon 을 모르는 사람도 읽혀야 한다.

그래도 적어 두는 이유는 **다음에 둘 중 하나를 손대는 사람이 다른 쪽을 보고 "불일치"로 읽을 수 있기** 때문이다. 불일치가 아니라 **역할 차이**다. 통일하려거든 어느 쪽 역할을 포기하는 것인지 먼저 정할 것.
