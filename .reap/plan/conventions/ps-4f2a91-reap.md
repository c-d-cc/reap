# ps-4f2a91 — 설계

root: `./docs/superpowers/specs/reap`

## 어떻게 읽는가

`README.md`가 색인이자 읽는 순서를 정한다. `01-concepts.md`부터 — 나머지는 전부 그것의 결과다.

문서 사이 참조는 파일 링크다. 섹션 번호로 인용하지 않는다 (문서가 자라면 번호가 밀린다).

## 어떻게 쓰는가

한 문서가 한 주제를 갖는다. 새 주제는 새 파일이고, 번호는 읽는 순서를 뜻한다.

**무엇이 참이어야 하는가**를 쓰고 **어떤 순서로 만드는가**는 쓰지 않는다 — 그건 milestone의 몫이다. 같은 것을 두 곳에 적으면 어긋나고, 어긋난 쪽을 구현자가 읽는다.

주장에는 근거를 붙인다. "이렇게 한다"보다 "이렇게 하지 않으면 무엇이 깨지는가"가 이 문서들이 실제로 하는 일이다.

## 도구가 이 소스를 어떻게 다루는가

`sources.yml`의 이 행을 `reap plan sources`가 읽고, milestone·loop의 `--ref ps-4f2a91:<파일>`을 `make`가 검증한다 — 파일이 이 root 안에 실재해야 한다(앵커는 안 본다). 문서 파일명을 바꾸면 그것을 인용한 열린 milestone의 `refs`가 깨진다. **바꾸기 전에 `grep -rn "ps-4f2a91:<옛이름>" .reap/vision`으로 인용을 찾는다.**

## 하지 말 것

- 실행해보지 않은 구현 코드를 넣지 않는다. 그것은 권위로 읽히고 결함이 그대로 옮겨진다
- 구현 순서·증분 경계를 넣지 않는다
